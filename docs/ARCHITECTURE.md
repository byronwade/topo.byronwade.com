# Topo architecture

## Product seam

Topo keeps the first vertical slice split across intentionally separate modules:

1. Framework adapters understand one framework's source conventions and emit normalized route descriptors.
2. API endpoint adapters inspect that same immutable source snapshot and emit normalized operations plus source issues without walking the project again.
3. Component preview adapters discover constructible variants and resolve runtime preview URLs without owning framework routes.
4. The scanner owns read-only source snapshots, validates adapter output, and emits a normalized graph without importing a framework implementation.
5. Capture workers turn routes and resolved component variants into local evidence artifacts.
6. The daemon exposes graph, context, scene, and artifact reads over a small loopback protocol and owns refresh timing.
7. Studio renders graph data and owns selection/layout presentation, not route, endpoint, or preview discovery.

The graph schema is the seam between them. Every normalized screen retains the exact route-discovery `adapterId` that emitted its candidate, and every API endpoint retains all contributing source and contract adapter evidence; route families and route-scene nodes aggregate route adapter IDs without importing adapter code into browser bundles. Durable project state stores graphs, route snapshots, accepted visual baselines, latest pixel comparisons, component preview artifacts, route-scoped interaction-probe artifacts, findings, and job lifecycles under `.topo/`; Markdown notes remain separate review records.

## API endpoint discovery

`@topo/endpoint-adapter` is a publishable version-one contract with one operation: `scan(context)`. The context contains project identity, package names, normalized source descriptors, and a read function backed by the scanner's existing immutable file cache. The registry validates adapter identity, methods, normalized paths, parameters, responses, issue records, and source containment before data enters the graph.

Two built-ins exercise the seam. `@topo/adapter-api-source` understands Next.js App and Pages handlers, Nuxt server handlers, SvelteKit server routes, literal Express/Hono/Fastify registrations, and Nest controllers. `@topo/adapter-openapi` reads conventional OpenAPI and Swagger JSON/YAML files and extracts operation metadata, parameters, request content types, response declarations, tags, security, and source locations. The scanner tracks only code plus conventional API-contract filenames, then executes framework, endpoint, and preview discovery concurrently over the same snapshot. A custom endpoint adapter can add another framework or protocol through `extensions.apiEndpointAdapters` without changing scanner ownership or triggering another tree walk.

The scanner merges operations by normalized `method:path`. Contract metadata takes descriptive precedence, while every source and contract discovery remains attached for provenance. Stable endpoint IDs use `api:http:<method>:<path>`. Computed router paths, malformed contracts, and adapter failures become stable source-located graph issues instead of silent omissions. Incremental source refresh reuses unchanged reads and reruns the bounded endpoint projection from the accepted snapshot; OpenAPI edits are tracked like code edits.

The graph, daemon, LLM/MCP projection, adapter inventory, and Studio consume this one endpoint model. Studio exposes a bounded visual projection—up to 200 operations on the canvas and 80 rows in the rail—while complete endpoint data remains available through the graph and paginated context query. Its usage panel derives source-screen and inferred-journey links from `flowTransitions` and inferred-flow steps on demand; it does not persist a second relationship store. This separation keeps DOM and rendering work bounded without truncating machine-readable project knowledge.

## Automatic project understanding

Project recognition is a normalized graph contract, not a startup heuristic hidden in the CLI. The framework registry already returns confidence, adapter identity, and reasons; scanner preserves those matches as `projectRecognition.frameworks` and derives capability records only from accepted graph or snapshot evidence. Routing, API, and component-preview capabilities point back to bounded source locations. Storybook, Playwright, testing, and TypeScript capabilities retain their package or file-convention reasons. Status remains `recognized`, `mixed`, or `unknown`, so a broad monorepo scan cannot masquerade as one confidently selected application.

Flow discovery is a separate version-one seam in `@topo/flow-adapter`. Its only operation is `scan(context)`. The context contains immutable source descriptors, package names, exact canonical screen identities, each screen's route module plus statically reachable value dependencies, and a snapshot-backed `readFile`. The registry validates adapter identity, source containment, screen ownership, target normalization, confidence, and source issues before a contribution enters the graph. `@topo/adapter-flow-source` is the built-in implementation for literal links, navigation and redirects, form submissions, `fetch`, and Axios. It reports computed navigation as an issue and never imports or executes project modules.

Framework, component-preview, and endpoint discovery run concurrently. Scanner then builds one Oxc dependency model and canonical screens before flow discovery, because flow ownership needs exact route-to-source reachability and API resolution needs normalized endpoints. This is still one filesystem snapshot and one read cache: flow adapters do not walk the tree or reread files outside the snapshot. Persistent `ScannerSession.scan(changedPaths)` replaces only reported entries, then deterministically recomputes recognition, transitions, journeys, graph edges, and issues from the accepted snapshot.

Each discovered action becomes a version-one `FlowTransition` with source screen and route, adapter, kind, action, source location, confidence, and a target resolved to a canonical screen pattern, API endpoint, or explicit unresolved route. Resolved transitions add source-located navigation or related edges. A bounded breadth-first derivation creates read-only `InferredFlow` candidates from entry routes and zero-indegree screens, capped at 24 candidates, 32 steps, and depth eight. Every candidate exposes confidence and `truncated`; none is persisted under `.topo/flows` or treated as user authority.

The daemon stores this accepted graph through its existing semantic-change and idle-coalesced durability path. Studio receives the same graph event, shows inferred candidates separately from recorded flows, and never enables flow mutation controls for derived evidence. Context schema version 7 projects project recognition in the project record plus independent `flow-transition`, `inferred-flow`, and `inferred-flow-step` records. A watcher-reported source change therefore updates graph, Studio, filesystem context, loopback queries, and MCP without a second model or full rediscovery.

## Adapter inventory seam

`@topo/adapter-inventory` owns one versioned, renderer-independent view across framework, API-endpoint, flow-discovery, component-preview, and application-runtime adapters. Its pure builder accepts the normalized graph, the bounded `topo/adapters/*/adapter.json` inspection, exact extension module lists from normalized config, and optional explicit runtime activation. It returns deterministic entries for built-ins, project scaffolds, configured-only modules, graph-observed framework, endpoint, flow, and preview contributors, plus every malformed-manifest issue. Each entry retains exact `screenIds`, `endpointIds`, `flowTransitionIds`, `inferredFlowIds`, and `componentIds`, so counts and relationships are derived from membership rather than a project-wide framework guess. Status is evidence-scoped: active graph contribution, exact registration, declaration-only, or built-in availability are never collapsed into one ambiguous “installed” state.

`@topo/protocol` re-exports the response schema and owns the `adapters` resource invalidation. The daemon builds a fresh response for `GET /adapters`, watches the repository-owned adapter catalog even when framework source lives in a nested monorepo application, synchronizes canonical context, and emits `resource.updated` without forcing a source rescan. `@topo/llm-context` consumes the same inventory to create searchable adapter records plus reciprocal route, endpoint, transition, inferred-journey, and preview ownership relationships. Studio validates the daemon response, uses one deterministic presentation grouping, exposes selected source provenance, and labels disconnected state instead of deriving adapter status from route names or package assumptions.

This seam intentionally describes capabilities and evidence; it does not become a plugin lifecycle. Runtime module loading remains inside the five narrow registries, the application graph remains source-derived, and adapter credentials or process environment never enter the inventory.

## LLM read model

`@topo/llm-context` is a derived, versioned projection across every durable product concept. It preserves each record's full structured payload while adding stable identity, concise summaries, searchable text, source locations, and typed relationships. Markdown notes and JSON flows remain editable source records; `.topo/state.json`, snapshots, and `.topo/llm/` remain derived local artifacts.

```text
application source + adapters -------> normalized graph ---\
.topo/notes/*.md ---------------------> note store ----------+--> @topo/llm-context
.topo/flows/*.json -------------------> flow store ----------+       | files / CLI / HTTP / MCP
.topo/state.json + binary artifacts -> durable state -------/
```

All agent-facing surfaces use this projection rather than maintaining separate interpretations. One graph-local index resolves canonical route identities, exact screen IDs, and source-to-screen membership for notes, flows, findings, probes, and adapter relationships. The projector constructs its fixed record envelope through a hand-written assertion equivalent to the exported Zod record schema, avoiding a deep clone of every already-typed payload; untrusted consumers continue parsing with the public schema, and the CPU benchmark parses the complete generated manifest and record set outside its timed interval. Relationship integrity remains a separate complete pass, so duplicate identities and dangling targets still become `issue` records.

Reads are bounded and paginated by default. Persisted operational history is also bounded: storage preserves every queued or running job and the newest 100 terminal jobs by default, while recording cumulative pruning evidence in the project record. Parse failures become explicit `issue` records. Preview secrets, signed sessions, environment values, cookies, headers, and local-storage values never enter the projection. The complete extension contract is documented in [LLM_INTERFACE.md](./LLM_INTERFACE.md).

## Doctor seam

`@topo/doctor` exposes one `runDoctor({ project, graph, probe? })` interface. The module owns check policy, stable identities, severity and process-exit meaning, bounded preview probing, remediation text, summaries, and sanitization. Its production probe inspects the exact Chromium executable through `@topo/browser` and performs one timeout-bounded request to the native preview origin. The pure `application.source-selection` policy compares the resolved roots with the graph's exact screen framework families: an unscoped project root spanning multiple families becomes an actionable warning, while a selected nested application or one-family root passes. Tests replace the complete runtime probe with an in-memory adapter; callers never coordinate filesystem, browser, network, or summary checks themselves.

`@topo/protocol` owns the versioned report schema and the `doctor` resource invalidation. The CLI renders the report as text or JSON. The daemon caches a startup report, refreshes it through `POST /doctor`, includes the latest timestamped evidence in serialized LLM-context writes, and publishes a typed resource event. Source-watch and diagnostic hot paths do not wait for Doctor's bounded network probe; they retain the latest explicitly observed report until the next run. Studio validates `GET /doctor`, renders its real timestamp and checks, and rehydrates after the event. Each check becomes one `doctor-check` context record available through files, daemon queries, CLI, and MCP.

Studio's Doctor presentation model is deliberately ephemeral. It composes severity filters over canonical environment, security, and application checks plus graph findings without changing their scopes or truncating records. The shared Studio selection API adds only a bounded `finding` address into the canonical graph; report rows, project search, the evidence rail, reload reconciliation, and production board checks all use that same identity. Remediation remains inert text until an explicit browser copy action and is never evaluated by Studio.

## Note lifecycle

`@topo/notes` owns the strict, versioned note and anchor schemas plus atomic Markdown persistence. Lifecycle status and anchor health are separate fields. Updates preserve creation identity, support explicit nullable clears, validate path-safe IDs, and replace files through a temporary write plus rename. Canonical colon-bearing IDs are percent-encoded as filenames while reads remain compatible with the earlier sanitized filename form.

The daemon exposes collection and item CRUD at `/notes` and `/notes/:id`. Every accepted mutation first persists the source record, regenerates canonical LLM context, then emits a typed `resource.updated` SSE event. Its file watcher classifies direct `.topo/notes/*.md` and `.topo/flows/*.json` changes as durable resource changes instead of source-graph changes. Generated `.topo/llm`, `.topo/state.json`, snapshots, and preview artifacts do not recursively trigger graph scans.

`@topo/cli` exposes `list`, `add`, `show`, `update`, and `remove` as one presentation adapter over that same `NoteStore` interface. The adapter owns strict option parsing, human or JSON rendering, and one injected context-resynchronization callback; it does not own Markdown encoding, identity rules, atomic writes, or update semantics. This keeps terminal, daemon, and Studio mutations converged on one persistence implementation while allowing the packed consumer to test the complete lifecycle without starting the Studio.

Studio applies note updates and deletes optimistically and restores the previous record when the daemon rejects the operation. The deterministic website demo uses the same lifecycle in memory. The Notes index search is a transient, order-preserving projection over one visible facet and the accepted Markdown plus structured anchor fields; it owns no competing index or durable record. Detail is inspect-first, keeps stable previous/next identity navigation and anchor evidence available, and mounts its title/body/delete editor only after explicit disclosure; cancel restores the accepted record. Re-anchor promotes the deliberately selected screen source and verification time, preserves already recorded DOM signals only for the same exact screen, clears stale drift distance, and never fabricates missing element evidence. Moving to a different screen drops the prior screen's signals and coordinates. The Notes detail view resolves screen evidence only through exact note targets, canonical routes, source identity, or explicit component `usedBy` relationships. It then uses the shared hybrid evidence stage for a signed live frame, newest route capture, or labeled unbound state. Normalized coordinates are projected onto that exact artboard; every missing signal remains **Not recorded**.

`apps/studio/src/note-composer.ts` is the pure creation seam between Studio selection and `WriteNoteInput`. Eight Paper-facing presets resolve through three target policies: exact selected screen, exact selected flow or step, and deliberately free-standing. The module never falls back to the first screen or flow, never emits an anchor, and never treats element or region selection as coordinate evidence. The Paper **Flow marker** preset is explicitly stored as a target-free `flow` note, preserving the seven-value durable schema. `AnnotatePopover` owns only the transient title/body form and target disclosure; `useTopoData.createNote` sends the resulting payload unchanged to the daemon or materializes the same version-one record in the deterministic demo.

`apps/studio/src/note-placement.ts` is the pure placement seam. It converts transformed client points into clamped, deterministic normalized coordinates, canonicalizes reverse-dragged regions, rejects undersized rectangles, and creates one existing `UpdateNoteInput` for the exact selected screen. Each deliberate placement creates fresh anchor evidence: a current live element inspection may add role, accessible name, locator, and DOM fingerprint, while a coordinate-only placement clears older semantic signals that the new point did not verify. `NotesWorkspace` owns only the transient armed, dragging, and bounded inspection state plus pointer capture. The shared evidence stage remains unaware of note mutation policy, and the resulting anchor continues through ordinary Markdown persistence, context projection, export, and MCP reads without introducing a canvas-only record.

## Flow lifecycle

`@topo/flows` owns one deep persistence interface for inspection, exact reads, upsert, partial update, and exact removal. The versioned schema validates path-safe flow and step IDs, entry references, branches, and cycles before any write. Canonical filenames percent-encode namespaced identities so `journey:checkout` and `journey-checkout` cannot collide; legacy sanitized files remain readable only when their embedded identity matches the requested flow. Atomic temporary-file replacement and one normalized path-keyed queue serialize complete read-modify-write operations across independent store instances, including on Windows.

The daemon exposes collection reads and creates at `/flows`, plus exact `GET`, `PATCH`, and `DELETE` operations at `/flows/:id`. A mutation persists first, rewrites the canonical LLM projection, and then emits the existing typed `flows` invalidation. Studio never mutates Pixi scene state directly: its inspector applies one optimistic source-record patch, rolls back on failure, and lets `@topo/layout` regenerate the directed scene from validated `nextStepIds`. Explicit demo mode uses the same pure patch functions in memory. Disconnected production mode is read-only because an in-memory note or flow mutation would falsely imply durability. CLI apply and update commands cross the same store interface rather than editing JSON with command-specific logic.

`createFlowScene` is the single renderer-neutral topology interface for Studio, daemon, and MCP. Its private implementation computes graph ranks and variable lane geometry, derives a bounded target from measured lane area, packs stable flow order across centered rows, and chooses the nearest rendered lane as supporting focus. The two focus identities remain explicit, but normal camera bounds frame the selected lane with bounded trailing stage space; this keeps the primary journey near native card scale and allows its nearby supporting lane to enter the composition without making the entire catalog the default viewport. Selected-step translation happens only after packing, and connection endpoints are emitted from the translated source and target nodes, so layout changes cannot invent or redirect a durable edge.

Live tracing is a bounded input path into that same lifecycle, not another store. `@topo/runtime-bridge` exposes one exact-origin subscription interface over the signed frame's capped sanitized event queue. `apps/studio/src/flow-trace.ts` is a pure transient projection: it accepts navigation events at or after the session start, deduplicates snapshot/live delivery, resolves concrete dynamic paths against the canonical graph, and emits one existing `WriteFlowInput` with explicit linear edges. App-level Studio runtime owns the ephemeral session so it survives the Flows-to-Routes transition; the selected route iframe owns subscription setup and reload refresh. Cancel drops only that memory. Finish calls the existing flow create action, so daemon persistence, atomic JSON, context regeneration, SSE invalidation, and scene rebuilding remain unchanged. The bridge never writes a flow and the recorder never retains credentials, arbitrary event payloads, or a parallel durable trace log.

## Review export seam

`@topo/exporter` exposes one `exportReview()` interface over normalized graph, Markdown-note, and snapshot-reference records. It owns format selection, inclusion policy, source and anchor representation, HTML escaping, SARIF mapping, file names, MIME types, and the invariant that binary snapshots are never embedded. The daemon, CLI, Studio, and MCP use this module instead of translating findings and notes independently.

The daemon's `GET /review` endpoint accepts `format`, `include`, and `snapshots` query options and returns the generated artifact with an attachment filename. Studio first generates the same artifact locally so explicit demo and last-validated disconnected sessions remain reviewable, then replaces only its body with daemon output when connected. An empty production session disables export instead of producing a demo-shaped report. `topo export` reads current diagnostics, note records, and durable snapshot metadata, creates parent output directories, and returns structured file evidence under `--json`.

## Source refresh lifecycle

Application-source changes enter a batched, serialized watcher queue. The daemon owns one `@topo/workspace` scanner session and one per-file static-analysis session. They load configured framework and preview adapter modules once, retain unchanged source and findings, and update only watcher-reported paths. Additions and removals update both snapshots; directory events, invalid paths, and explicit manual refreshes conservatively perform complete discovery. Every refresh executes the same adapter registries over the resulting immutable snapshot and rebuilds the complete normalized graph, so adapters remain stateless and framework-neutral instead of acquiring a second incremental contract.

`@topo/graph` compares the previous and next graphs with normalized changed paths. Direct route evidence produces an exact screen impact; component implementation or preview evidence produces that component plus its known `usedBy` screens. Files that cannot be attributed safely, such as shared layouts, CSS, configuration, or transitive dependencies, produce a conservative all-visual impact. Reconciliation preserves capture status for every unaffected screen and resets invalidated screens to the newly scanned state.

The daemon compares normalized graph content without treating `generatedAt` as a product change. A semantic no-op keeps the accepted graph and skips state/context rewrites. A real graph or finding change becomes available to Studio in memory immediately, then enters one 500 ms idle-coalesced durability queue. New source events supersede intermediate pending graphs; bounded context, manifest, export, explicit resource writes, and daemon shutdown force and await the latest graph persistence plus complete LLM export. Graph events publish only after that durable projection succeeds. Fast scan jobs remain observable while active but do not consume terminal history.

When `preview.autoCapture` is enabled, the source lifecycle awaits that graph durability boundary before capturing only the planned route IDs and constructible affected component previews, persists the resulting evidence once, regenerates canonical context, and emits typed graph plus resource invalidations. Context query, manifest, and export endpoints wait for both active scanning and pending durability, so an API reader cannot observe a captured graph commit paired with the preceding projection. Capture failures remain honest job evidence and leave affected screens without a fresh captured status. Manual route capture, component capture, diagnostics, note, and flow operations use the same resource event families. Studio validates those protocol events with the shared Zod schemas and rehydrates durable resources rather than merging untrusted event payloads into local UI state.

## Parameterized route preview seam

`preview.routes` is a deliberately small mapping from canonical adapter-owned route patterns to concrete same-application request paths. `@topo/schema` owns path validation and the version-one `identity`, `configured`, or `unresolved` resolution. `@topo/config` normalizes the mapping; `@topo/scanner` materializes the resolution on every screen; and `@topo/graph` invalidates prior visual evidence when the resolved browser path changes. Canonical `routePath` remains the identity used by graph edges, atlas families, notes, flows, findings, search, filters, and queries.

`@topo/snapshots`, `@topo/diagnostics`, and `@topo/live-frame-host` accept only the resolved concrete path. Snapshot and interaction artifacts retain canonical `routePath` plus optional `previewPath`, while unresolved parameterized routes fail closed without launching a browser or mounting an iframe. Doctor exposes the missing canonical patterns as sanitized evidence. Studio shows the concrete path in the inspector or setup guidance and disables browser promotion until a mapping exists. The LLM project record carries the sanitized mapping, each route record carries its versioned resolution, and configured entries create explicit `configures-preview` relationships. Cookies, profile headers, local storage, signed sessions, and environment values remain outside this seam.

## Visual comparison seam

`@topo/snapshots` exposes two visual-review operations: capture graph evidence and accept one screen's current capture as its baseline. The module owns baseline identity, path containment, hash short-circuiting, PNG decode, pixel thresholds, dimension-change semantics, diff-file naming, and comparison persistence. Callers pass only the project root and stable screen identity; the daemon and Studio do not implement image-comparison policy.

Baseline images continue pointing at immutable hash-addressed snapshot files. Later captures first compare SHA-256 identities, so unchanged screens perform no PNG decode or pixel allocation. Only changed hashes use Pixelmatch, and diff images are written under `.topo/comparisons`. A comparison failure is recorded independently from capture status because a successfully observed screen remains valid evidence even when its review comparison cannot be produced.

Storage retains one accepted baseline and one latest comparison per screen in the version-one state envelope, with missing arrays normalized for backward compatibility. Every store instance targeting the same normalized state path participates in one process-wide operation queue, so capture, job, diagnostic, and baseline modules cannot lose one another's read-modify-write updates or race atomic replacement on Windows. The daemon's small `/visuals` and `/visuals/baseline` interface exposes those records, publishes a typed `visuals` invalidation, and serves root-contained image bytes. Canonical context projects `visual-baseline` and `visual-comparison` records with screen, snapshot, and baseline relationships; MCP uses those same records and image resources.

## Source intelligence seam

`@topo/parser-oxc` owns one compiler-backed source-intelligence module with two interface operations: parse one source identity or a deterministic batch. Its implementation uses the native Oxc Node binding in fast mode, direct ESM metadata, and the JavaScript, JSX, TypeScript, or TSX AST to return a compact versioned read model: value imports and aliases, value re-export dependencies, callable export shape, conservative required-prop counts, source lines, and recoverable diagnostics. Oxc AST nodes, visitors, native handles, and parser options do not cross the seam. A 4,096-entry source-identity LRU is an implementation detail that lets unchanged daemon scans reuse results.

`@topo/scanner` owns the next level of interpretation. Its small `ScannerSession.scan(changedPaths?)` interface serializes state transitions: omitted paths discover a complete immutable source snapshot, while reported paths replace, add, or remove only those entries before the complete graph is derived again. Directory or invalid-path uncertainty fails over to complete discovery. Each graph derivation memoizes one filesystem read per snapshot, executes framework and component-preview registries concurrently, resolves only relative dependencies that end at another listed snapshot file, and computes route-to-component coverage through the resulting directed module graph. Value barrels and intermediate feature modules remain traversable; type-only imports do not become runtime usage. The built-in Topo preview adapter consumes the same parser interface for safe callable-export and required-prop decisions. Third-party framework adapters still receive only the narrow read-only source-snapshot contract and do not need to understand Oxc or incremental refresh.

Parser recovery never means silent success. Source-located Oxc diagnostics become ordinary graph findings, and a component with a parser error is `blocked` rather than incorrectly marked renderable or missing. Diagnostics, coverage, and component state therefore reach Studio, exports, LLM context, and MCP through existing graph contracts without inventing a parser-only durable store or executing application code.

## Extension architecture

`@topo/framework-adapter` is the versioned framework-discovery seam. `@topo/endpoint-adapter`, `@topo/flow-adapter`, and `@topo/preview-adapter` independently own API, source-flow, and component-preview discovery. `@topo/application-runtime` is the native development-process seam. `@topo/scanner` consumes these contracts without importing an implementation. `@topo/workspace` composes the Next.js, TanStack, React, Vue, Nuxt, and Svelte route packages plus built-in API, flow, and preview adapters with project extensions, while the runtime module composes Next.js, TanStack, Nuxt, Vite, generic package-script, and project-installed process adapters behind one lifecycle interface. Adding a framework or flow convention does not add routing conditionals to scanner, graph, daemon, Studio, or LLM projection code.

```text
@topo/adapter-next -----------\
@topo/adapter-tanstack -------+--> @topo/workspace --> @topo/scanner --> @topo/schema
project adapter modules ------/              |                |
                                                composition      read-only snapshot

@topo/adapter-storybook ------\
@topo/adapter-topo ------------+--> @topo/preview-adapter registry --/
project preview modules -------/
                                      |
                                      +--> external runtime URL
                                      `--> @topo/preview-runtime (lazy loopback Vite host)

@topo/adapter-api-source ------\
@topo/adapter-openapi ----------+--> @topo/endpoint-adapter registry --\
project endpoint modules -------/                                      |
                                                                        +--> normalized graph
@topo/adapter-flow-source -----\                                       |
project flow modules -----------+--> @topo/flow-adapter registry ------/

Studio component action --> daemon protocol --> @topo/preview-scaffold --> colocated source draft
                                                  |
                                                  `--> scanner refresh --> graph finding or preview

Next.js runtime ---------------\
TanStack/Vite runtime ----------+--> @topo/application-runtime --> native dev process
generic dev script -------------+
project runtime modules --------/
```

Each contract accepts explicit dependencies and returns normalized results. Discovery adapters cannot reach scanner internals, mutate the application, or return source files outside the snapshot. Adapter IDs, framework IDs, detection evidence, confidence, route paths, screen states, preview identities, locators, source paths, priorities, readiness selectors, command plans, and API versions are runtime-validated before graph construction, capture, or process startup. Component-preview resolution receives an adapter-specific base URL and injected fetch implementation; application-runtime resolution receives only package metadata and the configured host and port, not scanner state.

Preview source creation is deliberately outside every discovery adapter. `@topo/preview-scaffold` exposes one deep renderer-independent boundary for no-write inspection and atomic no-overwrite creation. The daemon is its loopback transport adapter; its source-writing route rejects browser origins that are not loopback, while origin-less local process calls remain available. Studio is a consumer rather than the mutation owner. A successful write enters the same serialized scanner lifecycle immediately. Zero-required-prop output becomes an ordinary colocated preview, while required-prop output stays inactive and produces an ordinary source-located graph finding until a developer supplies deterministic fixture values. The package validates containment and real paths, selects an exact callable export from Oxc metadata, and never receives preview profiles or secret values. A future CLI, editor, or framework integration can reuse this boundary without importing Studio or changing the preview-adapter contract.

`preview.components` deepens the built-in Topo preview adapter without introducing another registry or scanner branch. The keyed configuration maps a component source path to one or more exact zero-prop wrapper exports. `@topo/config` normalizes the compact single-object or list form and rejects escaping paths; `@topo/workspace` constructs the same Topo adapter with those entries; the adapter verifies files and exports against the scanner snapshot and emits ordinary preview contributions. Configured and explicitly accepted generated wrappers therefore use the existing capability runtime, capture worker, Studio inspector, and LLM projection. Their `discovery` provenance and fixed priority survive in the graph, while accepted generation remains a project-authored trust marker rather than mutation authority for Topo.

`@topo/preview-runtime` owns only standalone React component construction. The daemon starts it lazily when the selected component set contains a `topo` source, injects the actual capability-scoped base URL into the generic preview registry, caches one process, and closes it with the daemon. It binds only to loopback, defaults to an ephemeral port, uses a random 256-bit path capability, and validates every requested source against the project root and a closed JavaScript/TypeScript extension list. Native application routes continue to execute through their framework development server.

Storybook remains an external-runtime adapter on the same generic capture path. Source scanning identifies exported CSF states and exact lines without loading project code. At capture time, the adapter asks the running Storybook index for the matching import path and export name, then gives Playwright the returned iframe ID. The permanent React/Vite fixture verifies this boundary against a real Storybook build, loopback static host, Chromium renderer, and content-addressed artifact store; mocked index tests remain compatibility coverage rather than runtime proof.

Future extension families should receive their own narrow, typed registry when at least two real implementations exist. Framework discovery, component previews, diagnostics, exporters, renderers, and storage providers must not be combined into a catch-all plugin lifecycle.

## Studio composition seam

`@topo/studio-api` owns the React-independent `defineStudio()` composition and route-matching contract, including keyed replacement and explicit destination/command removal lists. It also owns the compact shipped-default inspection surface: `studioBoards`, `studioFrame`, and `findStudioBoard()`, plus the bounded mapping between stable screen, component, flow, flow-step, and note identities and their Studio query parameters. Each board carries one stable ID, direct path, role, ready selector, layout, optional shell mode, optional renderer, and optional theme. This is acceptance data rather than a closed router union; project composition remains free to add or remove destinations. `apps/studio/src/studio-config.tsx` specializes the composition contract and exposes `customizeStudio()` as the one-call built-in extension path. The common case requires only a component for a destination or a function for a command; IDs derive labels and paths, while shell metadata receives safe defaults. Partial objects edit built-ins without copying them. The lower-level fully explicit definition remains available for advanced composition. `apps/studio/src/App.tsx` contains no destination render switch or command inventory: it resolves one active component, owns its Suspense loading and keyed error boundary, derives navigation, command palette entries, chrome, and status from the composed definition, and exposes current board/destination/view/overlay identity as stable DOM evidence. `apps/studio/src/studio-selection.ts` is the one pure reconciliation boundary: hydrated inventories correct stale pointers deterministically, empty loading inventories retain inbound identities, and a selected step cannot escape its selected flow. URLs remain ephemeral presentation pointers rather than durable application data.

`apps/studio/src/studio-runtime.tsx` is the bounded React seam for custom views. It groups normalized data, location, selection, actions, settings, and a three-call canvas controller (`mode`, `setMode`, and `fit`) rather than exposing shell internals as individual props. `actions.go(destinationId, view?)` is the stable navigation helper; absolute-path navigation remains available. `apps/studio/src/api.ts` is the source-preview export surface. Built-ins live in `defaultStudio`; the checked-in `studio` export is the single customization point. Runtime validation rejects malformed paths and ambiguous route roots. See [Studio extensions](./STUDIO_EXTENSIONS.md).

Installed projects use a smaller data-only seam. `@topo/protocol` owns the browser-safe `StudioCustomizationSchema`; `@topo/config` validates its `topo.config.ts` input, the daemon serves the normalized schema-version-1 object from `GET /studio`, and `apps/studio/src/project-studio.tsx` composes it over the source definition. A configured destination contains a loopback HTTP URL instead of executable module code. Studio supplies the icon, chrome, status, and sandboxed iframe while the production host allows only validated loopback origins. Commands are declarative navigation records. This keeps installed customization portable and auditable without evaluating arbitrary project modules in the privileged Studio process.

Project composition is fail-safe at both boundaries. Schema-invalid manifests stop configuration loading with actionable validation. A schema-valid manifest that would create an ambiguous route root is ignored as one unit; the built-in Studio remains usable and reports the issue. The normalized manifest is included in the canonical project context record and context manifest, making additions and removals visible to agents as structured data.

## Studio search seam

`@topo/studio-api` owns the React-independent search record, target, selection, result, and in-process index contracts. `apps/studio/src/studio-search.ts` projects the canonical records already hydrated by Studio into those compact search records. ## Bounded job history

`@topo/storage` owns terminal-job retention instead of leaving each caller to trim arrays. Every write and startup compaction preserves all queued and running jobs, sorts evidence deterministically, and retains the newest 100 completed or failed jobs by default. Embeddings may inject another positive limit. Legacy version-one state without retention metadata is migrated in place through the same atomic writer; repeated startup does not double-count pruned records.

`@topo/jobs` exposes jobs together with `{ terminalLimit, retained, pruned }`. The daemon returns that versioned envelope from `GET /jobs`, and `@topo/llm-context` includes the retention object in the canonical project record. Individual retained jobs remain ordinary `job` records. This keeps current work complete, keeps state growth bounded, and tells humans and agents exactly when terminal history is partial.

Studio composition does not create a catch-all product plugin lifecycle. Framework and component discovery stay in their own adapter registries, and every new durable data concept must still enter `@topo/schema` and the canonical LLM read model.

## Cache management

`@topo/cache` is the deep module for disposable local working data. Its public surface has two operations: inspect one project's cache and clean it with an optional dry run. Internally it owns recursive accounting, deterministic ordering, path normalization, containment checks, symbolic-link leaf handling, cleanup, and recreation of the empty root. Callers do not reimplement filesystem policy.

Its complete mutation authority is `<projectRoot>/.topo/cache`. A normal directory is cleaned one contained child at a time; a cache-root file or symlink is replaced with an empty real directory. Recursive inspection uses `lstat` and never traverses links. This deliberately excludes `.topo/state.json`, snapshots, component previews, notes, flows, installation metadata, and LLM exports. The protocol owns versioned browser-safe report and request schemas. ## Local Studio hosting

`@topo/studio-host` is the portable production-asset seam. Its startup interface validates a real Studio bundle, binds a separate loopback HTTP server, contains decoded and symlink-resolved files inside the asset root, streams typed static assets, returns injected `index.html` for client routes, and owns idempotent shutdown. Its independent `inspectStudioBuild()` interface reads the Vite manifest, follows real static and dynamic dependency graphs, measures bytes from the artifact itself, and returns JSON-safe build evidence. It does not import the scanner, daemon, graph, or Studio React implementation.

`@topo/local-runtime` is the deep lifecycle module above the native application, signed profile gateway, daemon, and Studio host. `startTopoLocalRuntime()` accepts one resolved project and returns one immutable handle containing only public origins, profile names, lifecycle evidence, and an idempotent `close()`. Signed launch capabilities stay internal. Startup is transactional: a failure at any later stage closes every earlier stage before rethrowing. A runtime-only `previewPort` override supports collision-free automation without editing project configuration; it is limited to loopback HTTP and the daemon still distinguishes the native capture target from the clean gateway origin presented to Studio.

`topo dev` is a presentation adapter over that module instead of reimplementing process composition. The CLI resolves an explicit asset directory, an environment override, a package-bundled location, or the source workspace build in that order, then prints only public runtime evidence. The static index receives the daemon's actual post-listen origin through a fixed metadata placeholder, so ephemeral and overridden daemon ports do not become build-time assumptions. Studio resolves build-time configuration first, injected local evidence second, and uses the source-development default only when neither exists. It does not mark itself connected merely because SSE opened or a graph event arrived; the complete resource hydrate, including signed profile descriptors, must succeed before capability-protected live frames mount. The CSP allows self-hosted assets, the exact validated daemon origin for snapshot, baseline, and visual-diff images, exact configured frame origins, and `data:` image fetches used by deterministic demo textures; it does not emit Chromium-invalid generic IPv6 wildcard sources. Exact IPv6 daemon or frame origins remain admissible through validated configuration. Pixi's CSP-safe synchronization polyfills live inside the lazy GPU modules, removing their generated-function requirement without adding Pixi to a DOM-only destination or weakening the host's `script-src 'self'` policy with `unsafe-eval`.

The same hydrate is the production data-authority boundary. Before it succeeds, Studio uses `emptyApplicationGraph("Not connected")` plus empty resource collections and exposes **connecting** or **offline** through stable DOM evidence. Only `?demo=1` selects the Fieldbase fixtures. Every full hydrate starts a monotonic latest-commit lease; a newer SSE reconnect or resource invalidation makes every older in-flight response unable to replace validated state, warnings, or connection evidence. A disconnect after successful hydration preserves the last validated session graph for inspection but labels it stale; production note and flow writes fail before optimistic mutation until the daemon reconnects. This prevents fixture records, out-of-order responses, or volatile edits from being mistaken for current repository-backed application knowledge.

That boundary is runtime-enforced rather than TypeScript-only. Browser-safe note, flow, route-snapshot, graph, capture-policy, and evidence schemas live in `@topo/schema`; `@topo/protocol` composes them into schema-versioned project settings, notes, flows, snapshots, component-preview, and interaction-probe response envelopes. `GET /project` is a sanitized config projection containing package-derived identity, both roots, the config path, and only auto-capture, headless, and viewport policy. It never serializes executable paths or preview-profile secrets. Studio dynamically loads those validators and parses every hydration response plus every note or flow mutation response before state replacement. A malformed graph leaves the production shell offline and empty. A malformed secondary response leaves its previous valid collection untouched and raises a bounded warning. A separate synchronous exclusive-action lease is acquired before any optimistic note or flow update and before all other bounded Studio actions; the visible busy state reports that lease but is not the lock itself. Note and flow collection envelopes retain source-read issues so malformed files stay observable without becoming valid records.

Studio keeps project authority separate from browser preference. Project name, source root, auto-capture, capture viewport, and browser visibility are read-only config evidence. Theme, live-frame capacity, hover promotion, selected profile, and whether a Doctor rerun should include runtime probes remain bounded local preferences. The live-frame limit is normalized to one through eight before it reaches `@topo/live-frame-host`; the diagnostics preference invokes the existing explicit runtime endpoint instead of creating a second probe implementation. About metadata compiles directly from `docs/product.json`, so displayed version, distribution state, repository, documentation, issue, license, and release links cannot drift into a second hand-written product claim.

Pixi remains presentation-only, so every authoring and search control lives in semantic DOM. Visible inputs, textareas, and selects carry stable names plus native label associations; compact controls pair their Paper-matched visual treatment with the shared visually hidden label utility, and visual section captions use non-label text. Dark and light themes define separate error values while preserving the existing semantic token roles. The production board report records visible-control, unlabeled-control, unnamed-control, orphaned-label, and computed semantic contrast evidence for each state; it fails if a form defect exists or the faint-on-surface, faint-on-well, or error-on-active pair falls below `4.5:1`.

This module is deliberately separate from the daemon. API routes keep their existing protocol and port, the Studio can use ordinary client-side paths such as `/notes` without colliding with daemon resources, and future desktop or published-package adapters can replace asset resolution without changing project scanning.

## Native application runtime

`@topo/application-runtime` is the deep lifecycle module for the inspected application's real framework server. `startApplicationRuntime()` probes `preview.baseUrl`, returns a no-op handle when a healthy origin is reused, or resolves one confidence-ranked adapter and starts one process. Internally it detects the nearest declared package manager or lockfile, materializes cross-platform package-script commands, waits for an HTTP response, retains a bounded output tail, exposes unexpected exit evidence, and closes only the process tree it owns. The CLI starts this module before the daemon so initial captures and live frames never race an unavailable application.

The adapter seam has five built-ins—Next.js, TanStack, Nuxt, Vite, and a generic `dev` script—and accepts project modules through `extensions.applicationRuntimeAdapters`. Vite owns the common React, Vue, and SvelteKit command shape; Nuxt remains separate because its native CLI arguments differ. An explicit tokenized `preview.server.command` bypasses selection. Automatic startup is fail-closed to unavailable loopback HTTP origins; healthy origins are reused, remote and HTTPS origins are external-only, and managed mode refuses an occupied origin. On Windows, only validated `.cmd` or `.bat` package-manager shims enter a constrained absolute-path `cmd.exe` bridge; arbitrary explicit process commands remain shell-free.

Application process state is ephemeral operational evidence, not a durable project concept, so it does not create an LLM context record. Capture and diagnostics retain the configured native `preview.baseUrl`; the live daemon graph presented to Studio uses the clean selected profile-gateway origin and never the signed launch capability. Routes execute entirely in the native server. The already-validated project configuration is passed into the daemon when its source root is below the configuration root, preventing lifecycle and capture origins from diverging.

## Project and source roots

`@topo/config` exposes one `resolveProject()` interface that turns a CLI target into immutable `projectRoot`, `sourceRoot`, `configPath`, and parsed `config` values. `projectRoot` owns configuration and every durable Topo write. `sourceRoot = resolve(projectRoot, config.rootDir)` owns application reads, watching, preview construction, and runtime commands. `rootDir` is an explicitly trusted filesystem selector and may name a nested, adjacent, linked, or absolute application directory; resolution trims the value, rejects null bytes, and requires the resolved target to exist and be a directory before source discovery or process startup. Source containment is not treated as a security boundary because trusted project configuration can already select adapters and tokenized runtime commands. The security boundary is write ownership: storage, notes, flows, captures, cache, installation metadata, and LLM exports remain rooted under `projectRoot`. Keeping validation and resolution in one deep module prevents each CLI command, daemon subsystem, and adapter registry from assigning a different meaning to either root.

The daemon's interface accepts `projectRoot` and an optional pre-resolved `sourceRoot`. Storage, notes, flows, snapshots, preview artifacts, jobs, artifact containment, and LLM exports use `projectRoot`. Scanning, static diagnostics, the component preview runtime, and source watching use `sourceRoot`. Configured adapter modules resolve from `projectRoot`; adapters receive source-only evidence. When the roots differ, one watcher observes application source and a second watches only authoritative `.topo/notes` and `.topo/flows` records, avoiding duplicate source scans and derived-context feedback loops.

The normalized graph continues to use `graph.rootDir` for the source root because every graph source path is relative to that snapshot. LLM context schema version 2 makes this explicit with `projectRoot` and `sourceRoot` manifest fields and retains `rootDir` as a source-root alias. Operational code must not infer durable storage location from `graph.rootDir`.

## Reversible initialization and CLI distribution

`@topo/initializer` is the deep project-setup module. `planInitialization()` performs read-only project and tool detection and returns exact, hash-backed operations. `applyInitialization()` preflights the immutable plan, applies it transactionally, rolls back a failed operation, and writes the v3 installation manifest last. Uninstall is a separate plan/apply cycle that refuses partial restoration when any managed file drifted and removes only empty created directories.

`@topo/project-lifecycle` owns evolution after initialization. Its migration registry moves only known schema versions forward; the version-2-to-version-3 step adds package-spec and update timestamps without rewriting project source. Its update planner reconciles the currently installed package to the running CLI version, preserves unrelated package fields, reconstructs a current uninstall baseline with only Topo-owned keys removed or restored, and rejects missing ownership or a changed `topo` script. Plan application rechecks both package and manifest hashes, rolls back the package write if the manifest write fails, and returns the exact package-manager install handoff instead of modifying a lockfile. The CLI handles argument validation and bounded presentation; it does not duplicate lifecycle policy.

`@topo/cli` is built as one ESM executable with internal `@topo/*` modules bundled and third-party runtime dependencies left explicit. The same build invokes Vite against the production Studio and places the hashed static bundle beside the executable. Package contents are allow-listed to `dist` and the package README. The package contract rejects private manifests, private Topo runtime dependencies, missing Studio or license assets, and any tarball that cannot be installed, initialized, and uninstalled from an isolated fixture. This is package-readiness evidence, not npm publication evidence.

## Rendering model

Component packing remains private to the existing `createComponentScene` boundary. Scene version 2 derives a target width from measured group area, retains stable group order while packing multiple groups per row, centers narrower rows against the widest row, and preserves exact component membership plus selected-component and selected-group focus bounds. This deepens the renderer-neutral layout module without widening the Studio API, creating a Pixi-only taxonomy, or requiring a schema revision.

Flow packing likewise remains private to `createFlowScene`. Scene version 1 measures variable lane widths and branch heights, packs stable source order into adaptive centered rows, preserves selected-step world-origin anchoring, keeps a nearest-lane two-flow focus, and exposes selected-lane camera bounds with bounded trailing space without widening the interface or changing the schema. `FlowInspector` is inspect-first DOM presentation over that same record: compact evidence and step navigation are always available, while definition and step editors disclose independently and submit the existing optimistic mutations.

Every GPU surface mounts through the deep `@topo/renderer-pixi` application-host interface. That module owns bounded device density, stable renderer telemetry, resize bursts coalesced to one animation frame, queued-frame cancellation, initialization-failure cleanup, and idempotent teardown. Atlas, editor, and the shared topology renderer keep their distinct scene implementations while sharing the same browser lifecycle and failure behavior.

Component organization is one deep renderer-neutral module, not Studio-only state. `@topo/canvas-engine` classifies normalized component source paths into common feature, domain, module, route-local, shared, common, and component roots, then applies optional version-one `atlas.componentGroups` rules through deterministic longest-prefix ownership. It returns stable IDs, labels, configured/automatic provenance, exact membership, source prefixes, preview-status counts, preview count, and distinct route usage without importing layout, Pixi, React, daemon, or MCP code. `@topo/layout` scene version 2 adds only bounded row geometry and selected-component or selected-group focus bounds. Studio's searchable sidebar and Pixi renderer, the daemon endpoint, MCP resource/tool, and context schema version 7 all consume that same organization. Each component context record repeats its group placement for bounded reads, while configured groups add project `organizes-component` relationships. This preserves source and graph authority and prevents UI, automation, and LLM clients from drifting into separate taxonomies.

Studio uses PixiJS for GPU scene layers and ordinary React/DOM for inspector controls, source-backed evidence, and live frames. Every destination workspace is a dynamic entry. Atlas and Editor import GPU surfaces; Doctor Findings and Notes Detail lazily import the same evidence surface, while the Notes index, Settings, and Doctor report remain DOM-only. `apps/studio/src/screen-evidence.ts` is the pure selected-screen seam: it resolves one screen, its newest capture, explicit component usage, source-matched findings, and Markdown notes without inventing DOM structure. It maps a finding through exact source identity or component `usedBy`, and maps a note through an exact target, canonical route, anchor source, or targeted-component `usedBy`; an unbound note has no implicit first-screen fallback. `ScreenEvidenceStage` is the deep presentation module shared by Editor, Doctor, and Notes: it owns camera behavior, lazy Pixi grid loading, concrete configured preview-path resolution, signed live-frame promotion, snapshot fallback, explicit unseen states, renderer telemetry, and an optional canonical artboard overlay behind one small prop interface. It never becomes application authority and never fabricates element coordinates. `@topo/canvas-engine` owns the renderer-independent camera contract (`screen = world × zoom + offset`), anchored zoom, panning, deterministic per-axis start, center, or end fit math, deterministic group wrapping, and route-family organization. It forms one family from every canonical route path before assigning a district; the default state is the deterministic automatic-group authority when adapter states disagree. Each family then receives its nearest present parent, ordered children, and hierarchy level. Automatic domains larger than twelve families split into nested child districts only when at least three child prefixes contain two or more families; singletons stay with the parent. The version-one `atlas.routeGroups` config is a presentation policy over those canonical route paths: keyed rules carry a label, order, and one or more prefixes; longest-prefix matching assigns each family once, duplicate prefix ownership fails validation, configured groups bypass automatic splitting, and unmatched routes retain deterministic automatic organization. The policy never rewrites graph routes or source identities. `@topo/canvas-engine` then derives a stable region layer without changing district membership: automatic districts sharing one substantive root become one root region, remaining automatic roots become `section:top-level`, and configured districts remain independent project-owned regions. `@topo/layout` computes that model once and projects both the compact route map and full-size selected-screen layout from it, then produces the separate component coverage and directed-flow scenes. Flat areas select one, two, three, four, six, or eight grid columns; nested areas use hierarchy lanes with explicit parent-child connections. Each region chooses an adaptive bounded landscape packing width from its district geometry; ordered regions remain vertically sequenced, while narrower regions are centered against the widest region before hierarchy and navigation endpoints are calculated. Route scene version 4 retains exact section and district provenance, stable order, every represented prefix, exact section-to-district-to-route-to-screen membership, grid-or-hierarchy layout mode, screen-state membership, sources, render-status counts, route ancestry, hierarchy and navigation endpoints, whole-map bounds, selected-region bounds, selected-area bounds, and selected-screen bounds. The Pixi projection draws rounded region fields over one camera-anchored dot field, progressively reveals labels through deterministic zoom thresholds, draws hierarchy trunks beneath bounded route snapshot textures, highlights connections involving the selected screen, and lowers unrelated navigation evidence without removing it. Component scenes preserve unresolved `usedBy` evidence. Flow scenes consume only explicit `nextStepIds`, support branches and cycles without inventing edges, and classify every route binding. Daemon and MCP consumers add runtime Zod validation through the separate `@topo/layout/schema` entry so the Studio main bundle does not absorb server-side validation code. `@topo/react` exposes the camera contract as shared pointer, touch, wheel, pinch, Select/Pan mode, keyboard bindings, and shared fit alignment. `@topo/renderer-pixi` owns shared adaptive grid, allocation-bounded dot-field, and snapshot-texture primitives, while Studio's lazy topology renderer projects the component and flow scenes into a common GPU layer.

Captured screens are persisted under `.topo/snapshots`; captured component variants are persisted separately under `.topo/previews`. Binary bytes never enter the normalized graph. The loopback daemon returns route metadata from `GET /snapshots`, component metadata from `GET /component-previews`, and advertises extension-bearing `/image.png?v=<contentHash>` URLs so Pixi chooses its PNG parser before requesting bytes and a changed artifact receives a new cache identity. The previous `/image` paths remain read-compatible aliases. Either route streams an artifact only after `@topo/llm-context` verifies that its resolved path remains inside the project root. Component captures are requested through `POST /capture/components`, resolve adapter-owned runtime URLs, wait for adapter-owned readiness or error evidence, and persist success or failure independently per variant.

`@topo/canvas-engine` converts a camera and viewport into deterministic world-space visibility with overscan expressed in screen pixels. It also returns stable enter and exit deltas so renderers do not rewrite every container on every pan. Atlas applies that contract independently to route sections, district frames, route screens, and connection geometry; the shared topology renderer applies it to component and flow groups, nodes, and edges. Selection stays pinned even outside the viewport. Exact total, visible, and culled section, district, route, and connection counts are exposed as DOM evidence.

Atlas loads selected or nearby image URLs lazily with a hard four-request concurrency cap and a bounded viewport margin. Selection is prioritized, then candidates are ordered by distance from the viewport center. Route, component, and flow canvases share one `@topo/renderer-pixi` LRU through `snapshot-texture-cache.ts`: eight active textures may remain attached, while 48 entries or 128 MiB of estimated RGBA source memory bound the warm cache. Active keys survive the current prune pass; stale entries release their Pixi `Assets` source, and a per-URL unload barrier prevents rapid eviction and reload from racing. Each canvas publishes cache entries, bytes, retention, hit/miss counts, evictions, release failures, limits, and pressure state as machine-readable DOM evidence. Missing or failed artifacts retain a semantic fallback instead of leaving an empty node. The component canvas uses the first captured variant for each active component. The flow canvas maps a resolved step's `resolvedScreenId` to an existing route snapshot and never fabricates an image for unresolved or unbound steps. Atlas Routes opens in Map mode framed to the selected region with start alignment on the vertical axis, where viewport-intersecting region fields, route areas, compact route-family cards, status evidence, and navigation connections render without mounting application frames or loading selected-screen textures. That framing removes dead space above short regions while preserving a visible continuation into the next region. Selecting a card or using the explicit Screen control switches to the full-size selected-screen layout, promotes at most the bounded live-frame pool, and hydrates only relevant visual evidence. Fit Area frames the exact district and Fit Atlas exposes the complete regional map. Route and component navigators scroll changed selections back into view; component domains remain collapsed unless selected, explicitly expanded, or matched by search. The DOM telemetry reports mounted frames rather than merely eligible descriptors. Returning to Map removes those iframes while preserving route selection and deterministic focus geometry.

`@topo/live-frame-host` owns a renderer-independent DOM promotion policy. It admits at most the configured `maxLiveScreens` candidates, ranking selection, hover, and already-live world-space neighbors deterministically. Studio places the selected frame above its GPU snapshot at every zoom and exposes nearby background frames only in Atlas overview; selection and hover are interactive while background frames cannot intercept the canvas. All promoted frames share the GPU camera transform and signed gateway origin. Browser sessions remain owned by the capture and preview packages. `GET /atlas/organization`, `GET /atlas/scene`, `GET /atlas/components/scene`, and `GET /atlas/flows/scene` expose the same local policy and read models used by Studio. MCP mirrors the scenes through `topo://project/atlas`, `topo://project/components`, `topo://project/flows`, and one selection-aware tool per scene. Component capture metadata is available through `topo://project/component-previews`, a paginated tool, and exact `topo://component-preview/{id}/image` binary resources. Agents therefore never need to infer layout, route usage, flow topology, or component-preview identity from a screenshot.

## Signed preview profile boundary

`@topo/gateway` exposes a two-call lifecycle: `listen()` returns runtime session descriptors and `close()` releases every HTTP, TCP, and WebSocket resource. `topo dev` starts this gateway after the native loopback application is ready and before constructing the daemon. Each configured profile binds to a distinct address in the IPv4 loopback range, so Topo and application cookies cannot cross profile boundaries even though all sessions target the same native development server.

The first navigation carries an opaque HMAC-signed, expiring capability. The gateway exchanges it for an HTTP-only, secure, partitioned cookie, initializes only the profile's configured local-storage values through a nonce-bound bootstrap, and redirects to a clean route URL. Profile headers and configured cookies are injected server-side. Upstream response cookies are confined to the partitioned local preview context. HTTP bodies, redirects, CORS origins, and Vite-style WebSocket protocols are forwarded; framing headers are adapted only here.

`@topo/runtime-bridge` owns the framework-neutral browser contract rather than placing instrumentation policy in Next.js, TanStack, Studio, or the gateway. After session validation, `@topo/gateway` may buffer an eligible successful UTF-8 HTML response up to 10 MiB, inject the self-contained bridge before the document closes, remove stale entity headers, and add the exact SHA-256 source hash to the existing `script-src` policy when inline execution is not already allowed. Other CSP directives remain intact. Compressed, non-HTML, unsupported-charset, oversized, or already-instrumented responses remain unmodified or fail explicitly. The bridge exposes version 1, retains at most 200 sanitized events, strips secret-shaped payload keys, and accepts event subscriptions or anchor-inspection messages only from an exact loopback parent. Initial snapshots and subsequent events are correlated by source window, exact origin, version, and request ID; frame reloads require an explicit resubscribe. Missing or older bridges time out to coordinate-only placement or remain unrecorded instead of becoming fabricated semantic evidence.

The daemon publishes runtime descriptors at `GET /preview/sessions` so Studio can select a profile and preserve its launch capability while resolving route paths. The graph receives only a clean gateway origin. Native capture and diagnostic workers continue using the actual application origin plus an explicit profile, and signed descriptors are neither persisted nor projected into `@topo/llm-context`. The Studio host receives the exact clean gateway origins at startup and adds only those origins to `frame-src`.

## Performance contract

`apps/benchmark` exercises the same public module interfaces used by production code. `runTopoBenchmarks()` prepares deterministic workloads, defaults the standard profile to 21 measured samples after warmup, applies p95 budgets, and returns versioned JSON-safe evidence. `comparePerformanceReports()` is the promotion seam: it canonicalizes runtime, profile, workload, sample-count, budget, enforcement, and result identity into one fingerprint, refuses mismatches, requires both median and p95 to exceed tolerance before naming a trend, and independently rejects every hot p95 above 50 ms or a stricter workload target. Cold initialization and external browser/network cadence remain explicit classes with separate budgets. Temporary fixture creation and cleanup are not timed.

CPU/filesystem report contract version 2 contains six workloads. Complete discovery walks and reads the real temporary tree; incremental refresh mutates one source outside the timer, updates that path through one persistent scanner session, retains unchanged source and loaded adapters, and still rebuilds the complete normalized graph. Snapshot contents are then projected synchronously from the scanner's immutable cache, avoiding one promise continuation per unchanged file. The LLM workload receives a graph already accepted at its scanner/protocol/storage boundary and calls `buildLlmContextFromValidatedGraph()`; the public `buildLlmContext()` remains strict for untrusted JSON. Tests prove output parity and malformed-input rejection, while the runner parses the resulting manifest and every record outside timing. Built-in profiles scale from 100 to 5,000 routes and retain exact route, source, changed-file, component, flow, record, group, edge, and operation counts.

System report contract version 6 composes fourteen production paths on one fingerprint: 10,000-route Next.js, TanStack, React, Vue, Nuxt, and Svelte adapter discovery; separate 10,000-operation source API, OpenAPI, and source-flow discovery; 1,000-route daemon startup; complete graph HTTP; a real one-route add/remove refresh; explicit complete manual rescan; and a fresh-process packaged CLI help launch. Every framework, endpoint, and flow discovery result is independently capped at 50 ms p95. The API and flow workloads include registry validation and graph-ready or source-located records while excluding deterministic fixture construction. The semantic refresh target is the in-memory scan-to-graph handoff. The daemon reconciles scanner-owned graphs without cloning the complete graph through schema validation a second time; the public graph utility remains validating by default, and tests require the trusted and validated paths to produce identical canonical output. Graph persistence and full LLM file generation are coalesced derived work, while every context consumer forces that work before reading. This prevents rapid editor saves from exporting superseded megabyte-scale projections without weakening read consistency. Capture contract version 1 separately compares 20-screen orchestration and a real three-screen Chromium batch. Studio loading contract version 3 compares isolated cold destination loads with cached-history switches and requires every hot p95 to remain at or below 50 ms.

The renderer-neutral organizer owns one process-lifetime `Intl.Collator` for natural route-segment and component-name ordering. Context projection and scene construction both consume this deep module rather than maintaining separate sort implementations. The collator is immutable and constant-space: Topo avoids both repeated locale initialization on the hot path and an unbounded cache keyed by project route names. Framework adapters continue returning normalized records and do not depend on this implementation detail.

The `--browser` mode remains a separate execution seam while sharing comparison policy. Browser contract version 3 initializes the same `createPixiCanvasHost()` used by Studio and fails if its ticker starts. A temporary Vite server and isolated Chromium context measure that cold WebGL initialization, texture upload, bounded-cache pressure, sprite rendering, camera-frame work, external display cadence, and four-iframe promotion. The cache workload traverses 250, 2,000, or 10,000 candidates and asserts its active retention and hard limits. Three-phase heap evidence still separates baseline, active working set, and post-teardown retained heap after explicit CDP collections.

`runWebPerformance()` is the public-site seam. It opens five isolated 1440 × 900 Chromium contexts by default and records cold LCP, external TTFB, DOM readiness, load, CLS, DOM size, and maximum main-thread task. Studio startup uses complementary artifact contracts. ## Interaction-probe lifecycle

`@topo/analyzer-runtime` opens a fresh Playwright context, reloads the selected route before every candidate, and classifies each control independently. It compares URL/history, network requests, DOM and accessibility representations, dialogs, form submissions, downloads, meaningful focus movement, local/session storage, preview-bridge application events, and page errors. Default focus moving onto the clicked control is not counted as an effect. Browser failures become `activation-error` artifacts instead of aborting every other route.

The safety decision occurs before activation. Disabled, hidden, `data-topo-probe="skip"`, lexically destructive, and non-GET form controls are skipped; an isolated preview form can opt into a non-GET probe only with `data-topo-probe="safe"`, while destructive semantics remain excluded. `@topo/diagnostics` reconciles generated findings by stable ID and route scope. The daemon atomically replaces artifacts only for routes actually rerun, exposes exact-route reads at `GET /interaction-probes?routePath=...`, and refreshes the canonical context after persistence. Studio reads those records and requests `POST /diagnostics` with one explicit route. The same complete artifact is emitted as an `interaction-probe` JSONL/MCP record, including successful and safety-skipped observations that do not become findings.

The same deep module owns `runDiagnosticCheck()`, which projects a diagnostic run into the schema-version-1 protocol report used by CLI and CI. The report carries source/project roots, execution mode, route and severity policy, deterministic counts, findings, probe artifacts, and one `ok` decision. It intentionally excludes the complete application graph: canonical graph, finding, and probe ownership remains unchanged, while automation gets a bounded read and stable process-exit meaning. Runtime activation errors are high-confidence execution evidence and block any enabled threshold; `none` is an explicit advisory-only policy.

## Safety defaults

- Scanning is read-only.
- `topo init` refuses to overwrite an existing config file.
- The daemon binds to loopback by default.
- Native component previews use a per-process capability URL and cannot request source outside the project root.
- Capability URLs and tokens are runtime-only and never enter the normalized graph or LLM export.
- Runtime probes do not bypass production authentication and are opt-in local actions.
- Runtime findings remain probabilistic evidence backed by an isolated browser observation.
- Disabled, hidden, explicitly excluded, destructive, and implicit write controls are skipped before activation.
- The preview gateway only adapts framing headers inside a signed loopback session; production headers and authentication remain untouched.
