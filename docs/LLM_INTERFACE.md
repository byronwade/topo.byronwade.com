# Topo LLM interface

Topo treats LLM readability as a product contract. The PixiJS canvas is a presentation of application knowledge, never the only place that knowledge exists.

## Authority and derived views

| Concept                  | Source of truth                                                                                              | LLM representation                                                                                                                                                                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Routes and screen states | Framework source files and adapters                                                                          | `route` and `screen` context records with exact route-discovery adapter provenance                                                                                                                                                                                                                   |
| Project recognition      | Framework adapter matches plus graph and immutable snapshot evidence                                         | sanitized project recognition with framework confidence, adapter IDs, reasons, capabilities, bounded source references, and source-file count                                                                                                                                                        |
| API endpoints            | Framework handlers, router/controller declarations, OpenAPI/Swagger contracts, and endpoint adapters         | `api-endpoint` records with method/path identity, complete operation metadata, source and contract evidence, adapter ownership, security declarations, and queryable malformed-source issues                                                                                                         |
| Route preview examples   | `topo.config.ts` `preview.routes`                                                                            | Sanitized project mapping, versioned per-screen resolution, `configures-preview` project relationships, and actual `previewPath` on capture or probe evidence                                                                                                                                        |
| Adapter inventory        | Built-in catalog, `topo.config.ts`, `topo/adapters/*/adapter.json`, and graph observations                   | `adapter` records with exact kind, provenance, active/registered status, `screenIds`, `endpointIds`, `componentIds`, source, and bidirectional route/screen/endpoint/component relationships                                                                                                         |
| Components and coverage  | Application source, config, and exact adapter discovery                                                      | `component` records with source/export, discovery provenance, priority, readiness metadata, route usage, and exact automatic or configured atlas group placement                                                                                                                                     |
| Graph relationships      | Normalized application graph                                                                                 | `edge` records with confidence                                                                                                                                                                                                                                                                       |
| Atlas organization       | Framework routes, component source paths, and `topo.config.ts` `atlas.routeGroups` / `atlas.componentGroups` | Versioned `atlas` policy with config source references, `organizes-route` / `organizes-component` relationships, exact route hierarchy placement using canonical route-record IDs and reciprocal `parent-route` / `child-route` links, and exact component source-group placement on bounded records |
| Canvas topology          | Derived versioned route, component, and flow scenes                                                          | daemon scene endpoints, `topo://project/*` scene resources, and scene tools with exact route-region membership, component source-group membership, directed flow topology, and focus bounds                                                                                                          |
| Findings                 | Static/runtime analyzers and durable state                                                                   | `finding` records with evidence                                                                                                                                                                                                                                                                      |
| Doctor readiness checks  | Latest canonical environment/application/security report                                                     | `doctor-check` records with scope, status, evidence, remediation, and observation time                                                                                                                                                                                                               |
| Interaction observations | Isolated Playwright probes and `.topo/state.json`                                                            | `interaction-probe` records for effects, inert results, safety skips, and errors                                                                                                                                                                                                                     |
| Notes                    | versioned `.topo/notes/*.md`                                                                                 | `note` records retaining body, lifecycle, target, and complete structured anchor data                                                                                                                                                                                                                |
| User flows               | `.topo/flows/*.json`                                                                                         | authoritative `flow` and independently queryable `flow-step` records                                                                                                                                                                                                                                 |
| Inferred journeys        | source-backed transitions in the normalized graph                                                            | read-only `flow-transition`, `inferred-flow`, and independently queryable `inferred-flow-step` records with confidence, source, target resolution, adapter provenance, bounds, and relationships                                                                                                     |
| Route captures           | `.topo/snapshots/*.png` and state metadata                                                                   | `snapshot` metadata plus `topo://snapshot/{id}/image`                                                                                                                                                                                                                                                |
| Visual baselines         | explicit acceptance in `.topo/state.json`                                                                    | `visual-baseline` records plus `topo://visual-baseline/{id}/image`                                                                                                                                                                                                                                   |
| Visual comparisons       | capture hashes, pixel metrics, and `.topo/comparisons`                                                       | `visual-comparison` records plus optional `topo://visual-comparison/{id}/image`                                                                                                                                                                                                                      |
| Component captures       | `.topo/previews/*.png` and state metadata                                                                    | `component-preview` success/error evidence plus `topo://component-preview/{id}/image`                                                                                                                                                                                                                |
| Jobs                     | daemon queue and `.topo/state.json`                                                                          | active operations are observable through the daemon; durable operations project the newest 100 terminal `job` records by default, while sub-frame source scans remain transient and do not consume retained history                                                                                  |
| Preview profiles         | `topo.config.ts`                                                                                             | Name-only `preview-profile` records; secrets are excluded                                                                                                                                                                                                                                            |
| Capture policy           | `topo.config.ts` `preview.autoCapture`, `preview.headless`, and `preview.viewport`                           | Version-one sanitized policy embedded in the bounded `project` record; executable paths, profiles, headers, cookies, storage, and sessions are excluded                                                                                                                                              |
| Studio composition       | `topo.config.ts` and `apps/studio/src/studio-config.tsx`                                                     | Sanitized project manifest in the context manifest and `project` record; typed source registry plus a copyable extension fixture                                                                                                                                                                     |
| Project lifecycle        | `.topo/install.json`                                                                                         | Sanitized schema version, install/update times, Topo version, package identity/spec, package manager, and source root in the context manifest and `project` record; managed files, hashes, prior contents, and rollback evidence are excluded                                                        |
| Performance measurements | benchmark profiles and production Studio artifacts                                                           | Versioned benchmark, Studio build, loading, 23-board geometry/renderer, and profile-boundary reports with timings and environment context                                                                                                                                                            |
| Diagnostic quality gates | normalized graph findings and explicitly requested interaction probes                                        | Bounded schema-version-1 `topo check --json` report with mode, routes, threshold, counts, findings, probe artifacts, and pass/fail decision; the full graph is not duplicated                                                                                                                        |
| Derived working cache    | `.topo/cache`                                                                                                | Typed CLI and daemon reports; intentionally excluded from canonical context because every entry is disposable                                                                                                                                                                                        |
| Malformed records        | Unparseable adapter, API contract, computed endpoint, note, or flow source records                           | Visible source-located `issue` records                                                                                                                                                                                                                                                               |

`.topo/state.json`, screenshots, visual-diff images, component preview images, and `.topo/llm/` are derived local artifacts and are ignored by Git. Notes, flows, and `topo/adapters/*/adapter.json` manifests are source records and may be committed.

The project record and context manifest retain `projectRoot` and `sourceRoot` as separate evidence. `rootDir` may explicitly select a nested, adjacent, linked, or absolute application directory, but that does not transfer durable ownership: every `.topo` source record and derived artifact remains rooted under `projectRoot`. Agents can therefore inspect or operate on external application source without inferring that Topo may write project state beside that source.

Studio query identities such as `endpoint=<stable-id>`, `finding=<stable-id>`, `probe=<stable-id>`, and `preview=<stable-component-preview-source-id>` are navigational addresses into canonical records. An endpoint selection resolves only against the graph's exact `apiEndpoints`; a preview selection resolves only against the selected component's exact `previewSources` and newest matching `component-preview` artifact. Source order remains the deterministic default, and failed or absent evidence stays explicit. The `canvas=map` query is likewise a reload-safe presentation address for the route or component atlas, never route, screen, endpoint, component, or preview identity. These queries may be copied, searched, and reloaded, but they are neither durable records nor Doctor checks and never enter context exports or MCP as a second authority.

The normalized browser-safe contracts for graphs, notes, flows, route snapshots, findings, probes, and capture evidence live together in `@topo/schema`. Filesystem packages may re-export those contracts, but do not own a competing shape. `@topo/protocol` composes the same schemas into versioned collection envelopes and retains malformed note or flow reads as source issues. Studio validates those responses before either visual or agent-visible presentation state can consume them; a TypeScript cast is never acceptance evidence.

A local adapter scaffold is presentation and execution configuration, not a replacement for application source. The schema-version-1 adapter inventory deterministically merges sixteen built-in adapter capabilities—six framework, two API-endpoint, one flow-discovery, two component-preview, and five application-runtime entries—with valid local manifests, exact configured module specifiers, and graph-observed framework, endpoint, transition, inferred-journey, and component-preview contributors. It distinguishes `active`, `registered`, `declared`, and `available` rather than treating installed code as evidence of current use. Every entry carries exact screen, endpoint, transition, inferred-flow, and component membership, even when all are empty. Context schema version 7 projects each inventory entry as an adapter record. Project scaffolds preserve stable `adapter:<adapter-id>` identities; other provenances include their full inventory identity so adapters from different families with the same implementation name cannot collide.

The schema-version-1 `topo adapters check --json` report is ephemeral derived verification, not a new source record or context kind. It retains the selected manifest and module paths, exact adapter identity, four bounded checks, source issues, and pass/fail summary without duplicating the application graph or changing the adapter inventory. Malformed manifests remain explicit report issues and continue to project as canonical `issue` records through the normal inventory path. The check never includes preview profiles, environment values, headers, cookies, local storage, signed sessions, or tokens. It does import and execute trusted local adapter modules, while the application and development server remain stopped.

Every adapter record retains its complete inventory entry and an `extends-project` relationship. Active framework adapters add `discovers-route` relationships only for canonical routes formed from their exact screens; those route and screen records relate back through `discovered-by` and retain `adapterIds` or `adapterId` in structured data. Active endpoint adapters relate only to their exact `endpointIds`, while each `api-endpoint` relates back to every source or contract adapter that contributed evidence. Active component-preview adapters add `provides-preview` only for their exact components, which relate back through `previewed-by`. A local scaffold keeps its manifest source; configured-only modules point to `topo.config.ts`. The executable module remains ordinary project source and is never serialized into context. Invalid JSON, unsupported versions, or incomplete manifests become source-located `issue` records; Topo never silently loads them into the canonical read model.

`.topo/cache` is a narrower disposable working area, not another evidence store. Agents can inspect it through `topo cache inspect --json` or `GET /cache`, but its entries never become canonical records or relationships. Cleanup is therefore safe to automate only through Topo's contained cache API; snapshots, previews, state, and LLM exports remain outside that API even though they can be regenerated.

Doctor reports are ephemeral runtime evidence rather than a second configuration source. The daemon projects its latest report into canonical context during each synchronized write, and direct CLI/MCP context reads produce a fresh report. The stable `application.source-selection` record retains the configured `rootDir`, whether that selection is explicit, and the exact sorted framework families observed in the normalized graph, so an agent can distinguish one selected application from an ambiguous mixed-framework root without inferring scope from file paths. Records contain profile names only and explicitly mark `secretsIncluded: false`; preview cookies, headers, local-storage values, tokens, and environment variables remain excluded.

For TanStack Router projects, `routeTree.gen.ts` is an application-owned generated routing contract and remains readable source evidence. Topo projects its authoritative `fullPath` entries into normalized `route`, `screen`, and `edge` records; agents do not need to reverse-engineer route geometry or infer nested paths from filenames.

React Router and Vue Router source declarations, Nuxt page files, and SvelteKit route files enter the same canonical route, screen, source, and adapter records. Vue and Svelte single-file components remain ordinary source references and searchable component records; Topo does not serialize framework compiler internals. Static adapters omit ambiguous executable or relative route declarations instead of fabricating relationships, so a missing route remains observable as a coverage boundary rather than false agent context.

Parameterized route identity and browser execution are separate evidence. A route record always keeps the canonical framework path. Its `previewRoute` is version one and reports `identity`, `configured` with a concrete path and `topo.config.ts` source, or `unresolved` with remediation. The project record and context manifest include the sanitized `previewRoutes` mapping, and the project relates to each matching route through `configures-preview`. Successful snapshots and interaction probes retain the actual `previewPath` alongside canonical `routePath`; unresolved patterns remain queryable blocked screens rather than disappearing. No profile capability or secret is part of this mapping.

Component preview records preserve how each renderable state entered the graph. `discovery` is one of `storybook`, `colocated`, `configured`, `automatic`, or `generated`; `generated` means a project owner explicitly marked the source `ai-accepted`, not that Topo silently authored or trusted it. The component record retains every variant's component path, source path, export, priority, readiness, and provenance. A successful `component-preview` record adds the content-addressed image resource URI and capture evidence without replacing that source identity.

An explicit Studio preview-scaffold action may create project source, but it does not create a new context-record kind or bypass coverage evidence. An immediately renderable wrapper appears through the existing component and preview-source records after the daemon's synchronized rescan. A required-prop draft deliberately has no active preview export; the scanner emits the stable `component-preview-draft:<component-id>` finding with the draft path, component source, and completion guidance. That ordinary `finding` record is searchable through bounded CLI, daemon, JSONL, and MCP reads. Template hashes and creation responses are operation evidence, not durable project truth, and fixture templates prohibit credentials or environment values.

Visual review is equally explicit. A `visual-baseline` record means a human or authorized local caller accepted one current captured image as review authority; capture alone never implies acceptance. A `visual-comparison` record relates that baseline to the latest successful screen snapshot and retains status, both hashes, both dimensions, threshold, changed pixels, total pixels, ratio, comparison time, and any failure evidence. Unchanged hashes skip image decoding. A diff resource URI exists only when Topo produced a concrete changed-pixel image.

Performance reports are derived evidence artifacts rather than canonical application-context records. JSON preserves every sample, median, p95, maximum, workload dimension, latency class, budget, runtime fingerprint, status, and comparison trend; Markdown renders the same CPU/browser contract for human review. The comparison report refuses different profiles, runtimes, hardware, renderer identities, workload payloads, sample counts, or result sets. It requires both median and p95 to move before naming an improvement or regression, independently enforces the 50 ms hot-operation ceiling, and leaves cold initialization or external browser/network cadence visibly classified under their own budgets. CPU contract version 2 distinguishes complete discovery from a one-file persistent refresh and records the validated graph-to-schema-v7 projection. System contract version 6 retains separate 10,000-route discovery evidence for all six built-in framework families plus 10,000-operation source API, OpenAPI, and source-flow workloads. Browser contract version 3 identifies the real on-demand shared Pixi host, product-controlled camera work, external display cadence, native or SwiftShader adapter, and baseline/working/retained heap phases. Website contract version 1 records five isolated production navigations, LCP, TTFB, DOM milestones, long tasks, CLS, and DOM size. These reports let an agent compare like-for-like evidence without treating one machine as universal, an active allocation as a leak, a cold load as a hot interaction, or software rendering as native-GPU proof.

Diagnostic check reports are likewise derived assessment evidence rather than a second finding store. Their explicit threshold and `ok` field explain the process exit, while included findings and probe artifacts preserve stable canonical identities. The report contains no preview-profile values and omits the normalized graph, so an agent can inspect a check result without loading the application model twice; context queries and MCP remain the bounded interfaces for graph exploration.

Production Studio builds add `manifest.json` and schema-version-3 `studio-build-report.json` beside the bundle. The latter records the exact initial assets and raw/gzip sizes, five destination chunks, deferred Pixi, review-export, and strict-validation assets, fixed budgets, and six stable checks. Passing review-export and validation checks mean those modules are entry-reachable only as on-demand chunks; they are delivery evidence, not another review-data model. Schema-version-2 `studio-runtime-report.json` records the empty production offline state, rejected disconnected-write evidence, production Chromium request sets for direct demo Notes and Atlas routes, their observed readiness times, browser version, and nine stable checks. `studio-profile-report.json` records profile names, clean origins, observed header/cookie/local-storage roles, WebSocket protocols, and seven boundary checks; it never records the launch capabilities themselves. Schema-version-4 `artifacts/local-runtime/report.json` additionally records the real managed application, daemon, signed gateway, initial Screen, reload-safe zero-frame Map, final Screen round trip, and exact selected-screen retention. These reports describe delivery behavior; they do not replace the application graph or become a second source of route, flow, note, or finding truth.

## Canonical record envelope

Every record uses context schema version 7 and includes:

- `kind`, stable `id`, `title`, and concise `summary`;
- complete searchable `text` and kind-specific `data`;
- optional `routePath` and source file/line references;
- typed relationships to other context records.

The manifest and `project` record expose `projectRoot` for the directory that owns `topo.config.ts` and `.topo`, plus `sourceRoot` for the framework snapshot and sanitized `previewRoutes` when concrete parameter examples exist. The retained `rootDir` field is a version-2 source-root alias for readers migrating from the original contract. Agents must use `projectRoot` when locating durable notes, flows, captures, state, or exported records and `sourceRoot` when resolving a graph source path.

Relationship targets are integrity-checked after projection. Duplicate stable IDs and dangling note, flow-step, screen, or component references become queryable `issue` records and manifest warnings.

Projection creates one graph-local index for canonical route identities, exact screen IDs, and source-to-screen membership, then reuses it across adapter, finding, note, flow, and interaction relationships. Internally constructed records use a fixed-envelope assertion equivalent to `LlmContextRecordSchema`; the exported Zod schema remains the parser for untrusted input. The executable CPU benchmark additionally parses its complete generated manifest and every record with those exported schemas outside the timed interval. This optimization changes neither schema version nor searchable text, payloads, source references, relationship integrity, pagination, malformed-record visibility, or secret exclusion.

The implementation, validation, query behavior, kind catalog, and JSON Schema live in `packages/llm-context/src/index.ts`. New durable concepts are incomplete until represented there.

Studio composition is deliberately code-readable rather than canvas-only. Installed projects declare destination URLs, labels, paths, removals, and navigation commands in `topo.config.ts`; the normalized `studio` object is present in both the context manifest and the `project` record's data. Source builds keep React components, tools, commands, and status producers in one typed registry; the Paper inventory remains a separate machine-readable default-board ledger. Both APIs derive labels, routes, icons, and chrome defaults from compact entries. Composition describes presentation capability rather than replacing durable application data, so routes, flows, notes, findings, and captures continue to use the canonical record envelope above. Loopback frame URLs are visible; signed sessions and preview secrets remain excluded.

Exact local Studio selections are also code-readable. The stable query mapping is `screen`, `endpoint`, `component`, `flow`, `step`, and `note`; each value points to the corresponding canonical identity and is bounded before use. An agent may construct or retain one of these local links to direct a human to evidence, but the URL is not a context record and never outranks the graph, Markdown note, JSON flow, or other source record. Selection URLs contain no preview credentials or environment data.

Project lifecycle evidence follows the same rule. `.topo/install.json` remains the operational source for migration, update, and uninstall, while the context manifest and `project` record expose only its validated version, install/update times, Topo package version/spec, package manager, and source root. Managed-path inventories, content hashes, prior file contents, and rollback baselines never enter context. A missing manifest means the project has no install lifecycle evidence; malformed or unsupported metadata becomes a source-located `issue` record instructing the agent to run `topo migrate` rather than silently disappearing.

The route scene is also a complete nonvisual organization contract. Scene schema version 4 separates the compact `routeMap` from the full-size selected-screen layout. Each deterministic region includes its stable ID, label, automatic/configured/mixed provenance, reading order, represented prefixes, exact district, route, and screen membership, aggregate route/state/dynamic/status counts, and geometry. Automatic districts sharing one substantive root become one root region, remaining automatic roots become `section:top-level`, and configured districts retain independent project-owned regions. Each district still includes all represented prefixes, provenance, reading order, grid-or-hierarchy layout mode, exact route-node and screen membership, unique route count, total screen count, non-default state count, dynamic route count, maximum depth, aggregate render-status counts, and geometry. Every route node retains one stable renderer identity, primary screen, every screen state, every source file, dynamic status, render-status counts, nearest present `parentRouteId`, ordered `childRouteIds`, zero-based `hierarchyLevel`, and compact map geometry. The canonical route context record repeats its section, district, and hierarchy placement as plain JSON so bounded `route` queries do not require loading the full scene. Context projection deliberately translates compact scene identities such as `route:/jobs` into canonical record identities such as `route:tanstack-router:/jobs`; `hierarchy.parentRouteId`, every `hierarchy.childRouteIds` value, and reciprocal `parent-route` / `child-route` relationships therefore point to real schema-v7 route records. `hierarchyConnections` name each exact scene parent and child plus renderer-neutral endpoints; navigation connections separately name both graph screen endpoints and their route-family endpoints. Static sibling routes sort before dynamic or catch-all siblings, all states for one route remain adjacent even if adapter state records disagree on a group, and the scene exposes selected-region, selected-route-area, and selected-screen focus bounds. An oversized automatic domain with more than twelve route families splits only when at least three child prefixes contain two or more families; singleton routes remain in the parent district. Configured groups are never auto-split. Renderer-neutral geometry packs each region toward a bounded landscape target, retains ordered vertical region sequencing, and centers narrower regions inside the widest map bounds before connection endpoints are emitted. The project record points to `topo.config.ts` and relates configured organization to every matching canonical route. An agent can therefore reproduce and traverse the same region-to-area-to-route-to-state hierarchy and balanced placement shown by Studio without inspecting pixels or inferring ancestry or membership from coordinates.

Component scene schema version 2 is the corresponding nonvisual component-atlas contract. One pure organizer first recognizes common source-root-relative `features`, `domains`, `modules`, route-local, `components`, `shared`, and `common` structures. Project-owned `atlas.componentGroups` rules can then name, order, or merge one or more POSIX source prefixes; longest-prefix matching assigns each component once and duplicate exact ownership fails validation. Every group exposes stable identity, automatic/configured provenance, source prefixes, order, exact component membership, preview-status counts, preview count, distinct route-usage count, and geometry. The selected component exposes both focus bounds and complete selected-group bounds. Context schema version 7 repeats that group identity and aggregate coverage on each bounded `component` record. Configured ownership also adds `organizes-component` project relationships. Studio, daemon, MCP resources, MCP tools, and context queries therefore consume the same organization without deriving product domains from canvas pixels.

Component-scene geometry remains machine-readable rather than a canvas-only choice. Version 2 derives a bounded landscape target from measured group area, preserves source-group order across multiple rows, and centers narrower rows on the complete atlas. Agents receive the exact resulting group geometry through daemon and MCP scene reads while component identity, ownership, coverage, and relationships remain unchanged.

Flow-scene geometry follows the same rule. Scene version 1 derives variable lane dimensions from explicit graph ranks, packs stable flow order into centered landscape rows, and selects the nearest lane as supporting focus. `focusFlowIds` retains both identities, while `selectedBounds` frames the primary lane with explicit trailing stage space so a normal Fit keeps steps legible instead of scaling to the combined catalog extent. Exact step identities, route resolution, branch and cycle edges, selected-step anchoring, bounds, and translated connection endpoints remain available through the existing daemon and MCP scene interface; geometry never becomes flow authority. The inspector's edit disclosure is transient presentation state and does not create a second flow record.

### Recorded flow projection

A live trace session is ephemeral Studio input, not a durable concept or context-record kind. Its sanitized navigation observations are bounded, deduplicated, and canonicalized against the current graph in memory. **Finish** creates an ordinary `.topo/flows/*.json` record through `WriteFlowInput`; only after that accepted write does context regeneration expose the journey as one `flow` and independently queryable `flow-step` records with explicit relationships. **Cancel** creates no source or derived record. Concrete preview paths such as `/jobs/rf-1042` are stored as their canonical route binding such as `/jobs/:jobId` when the graph proves that match. Raw bridge events, timestamps beyond the flow description, network observations, DOM mutations, errors, credentials, and signed session data are never projected into the saved flow or LLM context.

## Inferred flow records

Automatic project understanding is derived from application source and the normalized graph; it is not another writable flow store. The project record embeds sanitized `projectRecognition` with status, framework matches, adapter IDs, confidence, reasons, capabilities, bounded source references, and source-file count. Recognition excludes package versions, environment values, executable code, preview capabilities, and secrets.

Each statically discovered action becomes one `flow-transition` record. Its stable data retains adapter, source screen and route, transition kind, human-readable action, exact source location, confidence, and a target that is either a resolved canonical screen, explicit unresolved route, or resolved/unresolved HTTP operation. Relationships identify the project, starting screen, resolved target, and discovering adapter. Computed destinations that cannot be represented safely become source-located `issue` records instead of transitions.

Each bounded traversal becomes one `inferred-flow` record and independently queryable `inferred-flow-step` records. The flow reports entry step, adapters, transition count, confidence, and whether the 24-flow, 32-step, or depth-eight limits truncated traversal. It relates to every step and source transition. Each step retains kind, action, route or endpoint identity, source locations, transition IDs, and explicit `nextStepIds`, then relates back to its flow, target screen or API endpoint, source transition, and next steps. These records are read-only candidates: they never receive `verified` status, overwrite `.topo/flows`, or become recorded-flow authority merely because Studio displays them.

All three kinds participate in normal JSONL export, bounded CLI/daemon queries, MCP structured reads, schema validation, pagination, and relationship-integrity checks. A source watcher refresh removes stale records after the same accepted incremental scan that updates the graph. Large agents can query them without loading the complete graph:

```powershell
topo context query . --kind flow-transition,inferred-flow,inferred-flow-step --query checkout --limit 25 --json
```

## API endpoint records

Each normalized operation becomes one `api-endpoint` record with stable identity `api:http:<method>:<path>`. The complete structured payload includes schema version, protocol, method, normalized path, title, operation ID, summary, description, frameworks, contributing adapter IDs, tags, parameters, request content types, responses, security status and schemes, plus every source or OpenAPI discovery record. Search text includes the method/path pair and all descriptive, request, response, framework, adapter, and source evidence; agents do not need to parse a rendered Studio card.

An endpoint relates to the project and each contributing adapter. Adapter inventory records retain exact `endpointIds`, allowing bounded reads in either direction. Source-handler and OpenAPI discoveries with the same method and path remain separate evidence inside one record, so an agent can distinguish executable implementation from declared contract without reconciling duplicate nodes. An `ANY` method means the source convention accepts or dispatches multiple methods but did not expose a safe static split; it is not rewritten as `GET`.

Computed registration paths, malformed OpenAPI/Swagger documents, and endpoint-adapter source failures become ordinary source-located `issue` records. They remain included in manifest counts, JSONL, Markdown, bounded queries, Studio search, and MCP. Topo never evaluates route factories merely to obtain a prettier graph. Endpoint records exclude headers, cookies, environment variables, profile storage, signed preview sessions, tokens, and runtime request bodies.

Large projects use the ordinary context pagination contract:

```powershell
topo context query . --kind api-endpoint --query "POST customer" --limit 25 --json
```

Studio may render a bounded subset for responsiveness, but it does not create a different endpoint model or truncate the canonical context projection.

## Source parser evidence

Compiler parsing is a derived discovery operation, not a new source of truth. The native Oxc read model drives the existing component `usedBy` relationships through snapshot-contained value imports and re-exports. Each component record therefore exposes the same transitive route coverage shown in Studio without asking an agent to infer usage from names or canvas positions. Type-only imports do not create runtime coverage.

Recoverable Oxc diagnostics become canonical `finding` records with a stable source-derived ID, exact file, one-based line and column, severity, parser identity, message, and confidence `1`. A component whose source has an error reports `previewStatus: "blocked"`. The malformed source remains application authority; Topo neither rewrites it nor hides it, and filesystem export, bounded query, Studio search, review export, and MCP can all read the resulting evidence through existing record kinds.

## Studio search

Studio search projects the same stable route, screen, API-endpoint, component, flow, flow-step, note, finding, interaction-probe, and Doctor-check identities used by the canonical read model. Every search entry is plain JSON data with a stable search ID, source target, destination, view, optional exact selection, searchable text, and evidence-oriented description. Endpoint results preserve their exact canonical endpoint ID and open `/atlas/apis`; every interaction result retains its exact canonical probe ID and, when known, the owning screen ID, so multiple controls on one route remain independently addressable. Selecting an entry delegates to ordinary Studio selection and navigation actions; the index does not create hidden entities or infer relationships.

The Doctor findings board follows the same rule. It chooses a relevant screen only through an exact finding-to-screen source match or a component record's explicit `usedBy` relationship, then renders the canonical screen and snapshot identities already available to context clients. If neither relationship exists, it retains the current screen instead of guessing from labels or copy. Source line and column evidence are not treated as visual canvas coordinates, so Studio does not create a pin that an LLM could mistake for canonical anchor data.

The search index is deliberately not another context-record kind. It is a bounded in-process presentation index over already readable source concepts, while CLI, daemon, filesystem, and MCP clients continue to query the canonical context model. API usage shown beside an endpoint is likewise derived from existing flow-transition and inferred-flow relationships; no canvas position or private UI selection becomes agent-facing authority. Preview cookies, headers, local storage, capability tokens, and environment values are never projected into search records.

The project record's `data.jobHistory` makes bounded persistence explicit. Durable terminal jobs use the configured newest-first limit, which defaults to 100; `retained` reports the current stored total and `pruned` is cumulative. Active operations remain visible through the daemon queue, but fast source scans intentionally disappear when they finish instead of becoming canonical history. Agents must not interpret a transient scan's absence, or an older pruned terminal job, as evidence that the operation never occurred.

## Note lifecycle and anchor evidence

Every note record retains the complete parsed Markdown object in `data`. Search text includes its `open` or `resolved` lifecycle, anchor status, author, target route and ID, and serialized anchor evidence. A source-matched anchor adds an explicit `anchored-to-screen` relationship; Topo does not infer a component, locator, role, fingerprint, or coordinate that was not recorded.

CLI `add`, `update`, and `remove` operations complete the Markdown mutation before regenerating this projection. Their structured output is the accepted source record, not an independent command model. The packed-consumer proof creates a deterministic namespaced note, finds its canonical `note` record through a bounded context query, updates and reads it, removes it, and requires the bounded query to return zero remaining records. Agents can therefore distinguish command success from verified projection freshness.

The six independently countable anchor signal families are source identity, component symbol, role or accessible name, test locator, DOM fingerprint, and normalized coordinates. Anchor health is `unbound`, `attached`, `drifted`, or `orphaned`; it is deliberately separate from review resolution. This allows a resolved note to retain a drifted anchor as historical evidence and allows an open note to remain correctly attached.

Studio's Notes index searches the selected facet across the same accepted note fields that remain available to context records—title, body, route, author, lifecycle, type, anchor status, and exact structured anchor strings. This is a bounded browser projection, not an alternate persisted search index, and it never alters record order or LLM relationships. Note detail follows only relationships already visible in that record model: an exact screen target, canonical `targetRoute`, recorded anchor source, or an explicitly targeted component's `usedBy` relationship. It has no first-screen fallback for unbound notes. Its default read state and previous/next navigation retain stable note IDs; the disclosed editor submits the existing validated mutation and cancel restores the accepted record. The canvas exposes the selected note, screen, snapshot, preview kind, and anchor status as stable DOM data, and projects a point or region only when `anchor.coordinates` exists. Choosing a different route creates an explicit re-anchor candidate; it does not mutate or imply a durable relationship until the Markdown update succeeds.

Element-pin clicks and region drags are transient UI input until a validated note update succeeds. The update records deterministic normalized coordinates, the exact screen target and source, `attached` status, and verification time in the existing Markdown anchor. A live element-pin request may add the current hit element's bounded role, accessible name, stable test locator, and DOM fingerprint through preview-bridge version 1. Every deliberate move replaces semantic signals with that current inspection; when no bridge or semantic response exists, the update remains coordinate-only and clears older signals rather than presenting them as evidence about the new point. Selecting a different screen also clears old signals and coordinates. The separate same-screen Re-anchor operation may preserve already recorded signals because it does not claim a new element location. Context export, bounded query, and MCP therefore read the resulting geometry and semantic evidence from the ordinary `note` record and `anchored-to-screen` relationship, never from Pixi state, raw client pixels, or a private bridge store.

Studio note creation follows the same closed-world rule before a Markdown file exists. The typed composer emits an existing `WriteNoteInput` only: selected-screen presets carry that exact screen ID and canonical route, selected-flow presets carry the exact flow or member step ID, and free-standing presets carry no target fields. Element and region presets do not emit an `anchor` until placement evidence is actually captured. The visual **Flow marker** choice is disclosed as a free-standing `flow` note rather than becoming an undocumented record type. The composer exposes its preset and resolved target kind as DOM data for bounded verification; those transient UI values do not create a second LLM record model.

## Filesystem export

Run:

```powershell
pnpm run topo -- context export apps/playground-next-app
```

Topo writes `.topo/llm/` containing:

- `manifest.json` — version, counts, warnings, kind descriptions, and file discovery;
- `schema.json` — JSON Schema for the context envelope;
- `context.md` — compact human/LLM discovery summary;
- `records.jsonl` — complete record stream;
- `records/<kind>.jsonl` — bounded per-kind streams.

Generated context is refreshed automatically by the daemon after scans, captures, diagnostics, note creates, updates, deletes, direct Markdown edits, and flow writes or direct JSON edits. CLI, daemon, and MCP reads inspect adapter manifests from source on each context build, so a scaffold is queryable immediately without a second registration database. A watched application-source change first updates the validated in-memory graph, then enters one idle-coalesced derived write. Rapid saves replace a pending intermediate graph with the latest accepted graph instead of exporting obsolete JSONL repeatedly. Context query, manifest, explicit export, resource mutation, and shutdown paths force and await graph persistence plus complete LLM export before returning; graph events publish only after that projection succeeds. Semantic no-ops retain the previous graph timestamp and require no export. Automatic capture awaits graph durability before writing fresh evidence. Unaffected screen capture status is preserved; affected screens report the newly captured state only after fresh evidence is persisted.

The project record also carries `capture.version: 1`, `autoCapture`, `headless`, and positive integer viewport dimensions. This is the same schema returned to Studio by `GET /project`, so a bounded `--kind project` query can answer how capture is configured without loading the complete graph or reading canvas pixels. No browser executable path or authentication-adjacent value enters that projection.

## Public showcase evidence

`apps/showcase-builder` emits a schema-version-1 `showcase-manifest.json` beside the generated public Studio files. The manifest is machine-readable distribution evidence: it identifies the generator, public asset and route bases, canonical demo entry, accepted Studio-build checks, stable source-report hash, and sorted per-file SHA-256 and byte records. It is derived, ignored output and never becomes a canonical Topo context record, project source, route, flow, note, or graph authority.

The showcase contains only the compiled Studio and its deterministic demo fixture. The builder removes the local daemon metadata placeholder, and neither the manifest nor generated assets may include preview cookies, headers, local storage, tokens, environment values, signed sessions, or inspected-project records. Agents use the manifest to verify what was packaged; they continue using bounded context queries and MCP for application knowledge.

## MCP

`topo mcp` uses the official TypeScript MCP SDK over stdio. It exposes:

- resources for the manifest, summary, JSON Schema, complete graph, versioned route/component/flow scenes, exact entities, route snapshots, accepted visual baselines, pixel-diff artifacts, and component preview artifacts;
- `topo_get_context_index`, `topo_query_context`, and `topo_get_entity` structured tools;
- bounded canonical queries include `adapter`, `interaction-probe`, `visual-baseline`, and `visual-comparison` records with their complete source, safety, and evidence data; paginated compatibility tools cover routes, notes, flows, findings, component previews, visual comparisons, and the full graph;
- `topo_get_atlas_scene`, `topo_get_component_scene`, and `topo_get_flow_scene` expose renderer-neutral groups, positions, focus bounds, route usage, branching, and connections;
- `topo_review_application`, a source-grounded review prompt.

All tools are read-only, closed-world, idempotent, and return both text and structured content where applicable. List and search tools are capped at 100 records per call.

## Security invariant

LLM context may include local source paths, adapter and preview identities, readiness selectors, note bodies, findings, capture images, and bounded semantic anchor evidence that has been persisted into a note. Native component-preview and gateway launch capabilities are deliberately transient and are not part of the graph or context record. The preview bridge's transient event queue and an unfinished or cancelled flow trace are not context sources. Context must never include preview headers, cookies, local-storage values, capability tokens, `.env` values, or signed gateway sessions. Profile names and clean local origins used by the runtime graph are the only authentication-adjacent values exposed; the browser verifier queries every live capability and requires zero context matches.
