# Features and status

The status labels on this page come from `docs/product.json`. “Available” means implemented and covered by repository evidence. “Preview” means implemented but still experimental. “Planned” has an adopted direction but is not available. “Considering” is a hypothesis, not a commitment.

## Application atlas

Component overviews use adaptive, renderer-neutral landscape packing. Topo derives a bounded target width from the catalog's measured source-group area, retains stable source order while packing multiple groups per row, and centers incomplete rows on the atlas. Exact scene width, height, and aspect are exposed as browser-readable telemetry so compact and desktop verification can reject a regression to an unreadable vertical strip without inspecting pixels.

Flow overviews use the same landscape discipline without weakening flow authority. Topo measures each lane from its explicit graph ranks, packs stable flow order into centered rows, frames the selected lane at readable scale while retaining its nearest supporting lane as nearby context, and exposes exact lane count, focus count, dimensions, and aspect as browser-readable telemetry. Every branch, cycle, route-resolution state, and connection endpoint still comes only from the versioned flow record.

Every normalized screen retains the exact route-discovery adapter that produced it. Route families and route-scene nodes aggregate those IDs, and the selected-screen inspector exposes the provenance without loading adapter code into Studio.

Topo normalizes a project into routes, screen states, component coverage, graph edges, findings, notes, and user flows. Studio presents those records through the checked 23-board destination and state contract. Editor is a source-backed evidence workspace, not a visual code editor: its selected artboard contains the real promoted iframe, the newest captured snapshot, or an explicit missing-evidence state. Its side panes are derived from stable screen, route, source, component, finding, note, and capture identities. Editor plus all three Atlas views use bounded PixiJS viewports with the exact Paper 14px side and bottom inset, 4px top inset, 16px clipping radius, a quiet camera-anchored dot field, explicit Select and Pan modes, anchored wheel zoom, pointer and touch panning, pinch zoom, keyboard controls, deterministic axis-aware Fit, and selection-aware level of detail. Routes opens on the selected full-size live or captured screen so source, findings, notes, and preview evidence remain readable at first contact. Its explicit **Map** control opens the complete compact route-family atlas at `?canvas=map`; **Screen** removes that presentation query without changing the selected canonical screen. Named regions contain exact route areas, and each area contains one semantic card per unique route, aggregates every screen state and render status, retains directed navigation connections, and switches into the existing full-size live or captured screen only when a route is selected. The shared route organizer forms route families before assigning districts, so an adapter disagreement between loading, error, and default states cannot duplicate one route across areas. It orders entry routes first, keeps route families and screen states adjacent, places static siblings before dynamic siblings, and exposes exact region, district, family, state, source, status, geometry, and focus metadata to Studio, the daemon, MCP, and route context records. Each family also records its nearest present parent, ordered children, and hierarchy level. Oversized automatic domains split into stable nested districts when the source graph contains at least three substantive child areas; singleton routes remain with the parent. Automatic districts sharing one substantive root become a readable root region, remaining automatic roots become **Top level**, and configured districts remain independent project-owned regions. This keeps a large `/workspace` readable as one region with focused Jobs, Customers, Reports, Settings, and similar route trees without requiring configuration. Small or flat areas retain balanced grids, while each nested district uses explicit hierarchy lanes and connections. Configured `atlas.routeGroups` remain authoritative and are never auto-split. Projects may use those keyed rules in `topo.config.ts` to name, order, or merge canonical route prefixes into product-specific districts. Longest-prefix matching is deterministic, duplicate ownership is rejected, and unmatched routes retain automatic organization. The layout packs each region toward a bounded landscape target, preserves region reading order, and horizontally centers narrower regions inside the complete map instead of producing a tall left-aligned spine. The route navigator uses that same read model for searchable regions, named areas, depth-indented routes, and explicit screen states instead of exposing repeated framework filenames; selection automatically returns its route family to view. Map presentation opens at the selected region, anchored near the top of the canvas so that region is immediately legible and the next product territory remains visible below it. Region provenance occupies a dedicated second header row, while measured title, count, path, and layout-mode widths suppress only trailing metadata that cannot fit; narrow areas therefore keep their identity without overlapping labels. The explicit **Area**, **Region**, and **Atlas** controls progressively reveal detail or the complete application. **Map** returns to the current semantic focus, **Screen** promotes the selected full-size evidence, and the percentage control refits whichever focus is active. Direct map links survive reload, and choosing a route from either the map or navigator returns to its exact screen evidence. Background navigation edges remain deliberately quiet while relationships touching the selected route receive stronger path and destination evidence. These presentation choices do not mount one DOM node or application tree per discovered screen. Components opens on the Paper coverage-and-evidence composition: a compact Renderable/Coverage gaps rail, one exact selected preview variant, and the readiness inspector. A component with explicit preview sources uses source order as its deterministic default or an addressable `preview=<stable-id>` selection, then displays the newest exact captured artifact, an explicit capture failure, or an honest uncaptured state with a capture action. Selecting a variant updates the Studio address and survives reload without changing component identity. A component without a preview source remains a visible coverage gap; its application screen is selected only through explicit component `usedBy` identity and uses the same bounded live iframe, newest snapshot, or honest missing-evidence stage as Editor. An addressable **Map** mode preserves the complete searchable source-domain topology and versioned scene; **Preview** returns without changing component or variant identity. One shared source-domain organizer still drives the searchable map sidebar, bounded Pixi overview, daemon scene, MCP scene, and component context records. Common `features`, `modules`, route-local, shared, and component directories form readable automatic groups; optional `atlas.componentGroups` rules name, order, or merge source-root-relative prefixes with deterministic longest-prefix ownership. The map sidebar collapses inactive groups around the selected source domain, expands search matches, and scrolls the selected component back into view. Every group retains exact component membership, aggregate preview status, preview count, route usage, provenance, and focus bounds, while each component still exposes its exact route consumers. Flows renders explicit `nextStepIds`, including branches, without inventing connections from array order.

Editor keeps its Paper-sized evidence tree, stage, and inspector while searching the complete default-screen and component inventories. Screen search matches route, title, source, framework, render status, and tags; asset and insert search match component name, source, preview status, and route usage. Dense relationship summaries remain bounded to protect the stage, but each one states its complete count and provides an explicit path to the owning destination. Clicking a finding selects that exact canonical finding before Doctor opens, so the URL, Doctor rail, report, and evidence canvas cannot silently fall back to the first project finding.

Visible route-family cards, selected route screens, and captured component variants become lazily loaded GPU textures, capped at four concurrent artifact requests. Map mode retains at most 24 visible route thumbnails; screen and topology detail retain at most eight selected or nearby textures. The route-family overview stays semantic and bounded regardless of state count; a missing image falls back to the route card, and selecting a route promotes only its exact full-size capture or live frame. One shared asset-aware LRU serves route, component, and flow destinations, while a 48-entry and 128 MiB warm-cache budget releases least-recently-used texture sources. A selected or active texture is protected during the current viewport pass; unavoidable pressure is reported instead of silently discarding visible evidence. Entries, estimated bytes, retained count, hits, misses, evictions, release failures, limits, pressure state, and visible hierarchy connections are exposed as deterministic DOM attributes. The renderer-neutral canvas module selects world-space intersections with screen-pixel overscan and computes stable enter/exit deltas; route sections, district groups, route families, hierarchy connections, navigation connections, selected screens, component nodes, flow nodes, and topology edges mutate Pixi visibility only when they enter or leave that view. The selected entity remains pinned. Every route canvas reports exact total and visible section, group, route, and connection counts alongside culled nodes. Resolved flow steps reuse their route's captured screen, while unresolved steps remain explicit semantic evidence. The DOM promotion pool is independently capped by `maxLiveScreens`, defaults to four, and ranks the selected screen first, an intentional hover second, then already-live nearby screens by world-space distance and stable identity. Live frames exist only in screen drill-down mode; the selected and intentionally hovered frames remain interactive while nearby frames are click-through. Every iframe is transformed by the same camera as its GPU snapshot. Texture loading remains observable and falls back to a semantic node if an artifact is absent or unreadable. Only the explicit `?demo=1` mode loads deterministic fixtures. Production Studio starts with zero project entities, labels connecting and offline state directly, and retains only graph data that its daemon validated during the current session. The graph, adapters, organization, notes, flows, snapshots, visuals, component previews, interaction probes, Doctor report, profile sessions, cache report, and Studio customization all cross runtime schemas before entering React or Pixi state. Invalid graph data keeps Studio empty and offline; a rejected secondary resource preserves the last valid collection and produces a visible warning. Versioned note and flow collection responses also carry malformed-source issues instead of silently dropping them. The versioned route, component, and flow scenes and their artifact metadata are readable from the daemon and MCP instead of existing only as pixels. See the [Studio Paper contract](./studio-paper-contract.md).

The public Fieldbase demo uses the same graph contracts as a connected project. Its 47 routes, 128 uniquely named components, ten source domains, 11 distinct Markdown-style notes, flows, findings, captures, and interaction observations retain stable source and target identities. Generic numbered component placeholders are prohibited by tests; coverage gaps therefore read as believable application evidence such as `AssignmentDrawer`, not generated filler.

Exact screen, component, flow, flow-step, note, finding, and interaction-probe selections are addressable through bounded stable query identities. Those links survive destination changes and reloads, while post-hydration reconciliation corrects stale identities, prevents a step from being selected under the wrong flow, and resolves a probe to its canonical owning screen. They point into the canonical graph, flow, note, finding, and interaction-probe models; they do not replace them.

Studio resolves the selected preview profile into a runtime-only signed session before creating live route frames, component captures, or diagnostics. Settings exposes every configured profile by name, while the clean profile origin remains visible and the opaque launch capability does not become application-graph data.

Parameterized routes retain their canonical framework identity while `preview.routes` supplies a project-owned concrete browser path. The configured path is used consistently by captures, live frames, and diagnostics, but route families, notes, flows, findings, source references, and searches continue to use the canonical path. A route without a concrete example remains visible and organized in the atlas with blocked preview status and actionable setup guidance instead of being requested literally or silently omitted.

## API endpoint atlas

Topo discovers application APIs in the same immutable source snapshot used for routes and components. The built-in source adapter recognizes Next.js App and Pages handlers, Nuxt server APIs and routes, SvelteKit server routes, literal Express, Hono, and Fastify registrations, and Nest controllers. A second adapter reads conventional OpenAPI or Swagger JSON and YAML contracts. Evidence with the same normalized method and path is merged into one stable endpoint rather than duplicated: source handlers retain executable provenance while an API contract contributes operation IDs, summaries, parameters, request content types, responses, tags, and security declarations.

The normalized graph stores each endpoint with versioned method, path, framework, adapter, source, contract, request, response, and security evidence. Computed router paths and malformed contracts become source-located `issue` records instead of disappearing. Studio's **APIs** view offers readable domain grouping, method and source/contract filters, honest zero-result states, source/contract evidence, response and security details, and stable selection. Selecting an operation also shows exact source screens and inferred journeys linked by canonical flow transitions; those links navigate through ordinary Studio actions rather than creating an API-usage model. Complete endpoint records are searchable through Studio, JSONL, loopback queries, and MCP. The visual projection is deliberately bounded to 200 canvas operations and 80 side-list rows while the canonical graph and agent interfaces remain complete and paginated.

API endpoint adapters implement one small `scan(context)` contract and receive the scanner's already-read files. Custom endpoint protocols therefore do not trigger a second filesystem traversal. The system-performance contract measures both built-ins against 10,000 discovered operations and keeps each hot p95 under 50 ms. See [adapter authoring](./ADAPTERS.md#api-endpoint-adapters), [the LLM record contract](./LLM_INTERFACE.md#api-endpoint-records), and [verification](./verification.md#api-endpoint-contract).

## Automatic project understanding

Every scan now emits an evidence-backed project-recognition record from the same immutable source snapshot used for route, component, and API discovery. It names every detected framework with adapter IDs, confidence, and reasons, then identifies proven routing, API, component-preview, Storybook, Playwright, testing, and TypeScript capabilities with bounded source references. An unrecognized or mixed project remains explicit; package names never become silent assumptions.

The built-in `source-flow` adapter follows each route module's statically reachable value imports and recognizes literal HTML or framework links, router navigation and redirects, form actions, `fetch`, and Axios calls. Topo resolves those transitions to canonical screen patterns or normalized API endpoints, keeps unresolved routes visible, and adds source-located graph edges without executing application code. Computed navigation targets become `flow-discovery` issues rather than guessed destinations.

Topo derives bounded read-only journey candidates from that transition graph: at most 24 entry journeys, 32 steps per journey, and eight traversal levels, with explicit confidence and truncation state. These candidates are not `.topo/flows` records and never replace recorded user flows. Studio labels them as inferred, exposes exact source evidence, and lets developers inspect them on the existing flow canvas. Context schema version 7 projects `flow-transition`, `inferred-flow`, and independently queryable `inferred-flow-step` records with complete relationships. One watcher-reported source change refreshes graph, Studio, durable context, and MCP reads through the persistent scanner snapshot.

Flow discovery is a public one-method adapter family. A project can register `extensions.flowAdapters`, scaffold `--kind flow-discovery`, or ship a package without changing scanner, daemon, Studio, or LLM code. All eight permanent framework fixtures prove recognition, source transitions, inferred journeys, context parity, native runtime behavior, and browser routes. See [flow adapter authoring](./ADAPTERS.md#flow-discovery-adapters), [the LLM record contract](./LLM_INTERFACE.md#inferred-flow-records), and [verification](./verification.md#automatic-project-understanding-contract).

## Studio project search

The global Studio palette searches the project, destinations, and actions from one keyboard-navigable surface. Project results cover routes and screen states, API endpoints, components, flows and individual steps, Markdown notes, findings, every interaction probe, and Doctor checks. Matching is deterministic, requires every query term, ranks title matches ahead of supporting evidence, and returns a bounded result set. An endpoint result retains its stable method/path identity and opens the API atlas; an interaction result carries its exact probe identity and owning screen instead of collapsing multiple controls on one route into one destination. The shell keeps the active Atlas surface readable at narrow sidebar widths, exposes counts through navigation semantics, follows arrow/Home/End tab movement, and removes disconnected or busy commands from the executable action list while explaining their unavailable state. Shortcut hints adapt to the host platform.

Each result retains a stable JSON-readable target plus the exact destination and view that own it. Choosing a route, component, flow step, note, finding, probe, or check first updates the ordinary Studio selection state and its addressable URL, then uses the public navigation action. Project extensions therefore do not need to know about ranking internals, and removed destinations cannot leave dead search results. Search index construction lives in an optional subpath loaded with the command palette, keeping ranking code out of the initial Studio shell. Search is a presentation index over canonical records, not a second source of project truth.

## Performance contract

Topo ships executable performance contracts instead of treating speed as an architectural aspiration. Its smoke, standard, and stress profiles measure complete filesystem discovery, one reported source change through a persistent scanner session, graph reconciliation, canonical LLM context projection, renderer-neutral Atlas scene construction, and shared pan/zoom camera math. The standard CPU profile uses 21 measured samples after warmup. Fixture generation, file mutation, one-time trusted-boundary validation, output-schema verification, and cleanup stay outside the operation they would otherwise distort.

Route and component organization share one immutable natural-text collator for the lifetime of the local process. Large scans therefore preserve numeric, case-insensitive ordering without recreating locale machinery inside each sort comparison, and the optimization benefits both the visual scene and the complete LLM read model without adding a project-sized cache.

Each versioned report includes exact workload dimensions, runtime and hardware context, every raw sample, median, p95, maximum, budget, and pass/fail result. `--baseline` compares a retained report with the new candidate, and the comparator rejects runtime, profile, workload, sample-count, or result-identity drift. A trend is promoted only when both median and p95 move beyond the declared tolerance; a noisy one-sided tail remains stable, while every p95 still crosses its independent target gate. Hot local work is capped at 50 ms or a stricter workload budget. Cold initialization and external browser/network cadence carry explicit latency classes and retain their own visible budgets instead of weakening the hot-path target. `--check` makes either a workload or comparison failure non-zero.

System contract version 6 measures real Next.js, TanStack, React, Vue, Nuxt, and Svelte route discovery plus separate source-code API, OpenAPI, and source-flow discovery at 10,000 operations, daemon startup and graph HTTP over 1,000 routes, one semantic add/remove route refresh, conservative manual rescan, and a fresh-process packaged CLI help launch. Every framework, endpoint, and flow discovery result is a hot workload with a 50 ms p95 ceiling. Source refresh owns persistent scanner and per-file static-analysis snapshots. Scanner output assembled from contract-checked adapters and typed analyzers uses an explicit validation-free reconciliation path, while the public/default graph seam still validates untrusted input. Semantic graph changes become visible in memory immediately, while one coalesced durability queue replaces superseded graph writes and LLM exports; bounded context, manifest, export, and shutdown paths force and await that queue before returning. Edits that change neither graph topology nor findings retain the accepted graph and skip derived rewrites. Active scan telemetry remains observable without filling the newest-100 terminal job history. The packaged CLI uses a 5 KB help bootstrap and imports its full command graph only for real commands.

Capture and Studio loading have independent comparisons rather than hiding browser work inside CPU totals. Capture reuses one Chromium process with a fresh isolated context per screen and commits snapshots, comparisons, and preview metadata in batches. Studio loading uses isolated production contexts, separate cold and cached-history samples, route-specific module preloads, and a hard 50 ms p95 gate for cached Notes and Atlas destination switches. Notes never preload Pixi; Atlas may preload only its route-specific GPU dependency graph. Cold WebGL/browser work remains visible under a separate budget.

The LLM workload accepts the same graph already validated by scanner, protocol, or storage boundaries, builds the complete schema-v7 record set, and parses the resulting manifest and every record through exported runtime schemas outside the timer. `buildLlmContext()` remains the strict parser for untrusted callers; `buildLlmContextFromValidatedGraph()` is the explicit deep seam that avoids a second full graph clone. Both paths are parity-tested on valid data, and the strict path still rejects malformed input. The scanner likewise projects its immutable source snapshot directly instead of scheduling one promise continuation per cached file during every graph rebuild.

`--browser` runs Playwright-controlled Chromium through the real shared `createPixiCanvasHost()`, snapshot texture cache, application sprites, viewport selector, visibility deltas, and bounded live-frame selector. Browser report contract version 3 asserts on-demand rendering—the shared Atlas, topology, and Editor hosts do not run an idle Pixi ticker—and separately measures product-controlled camera frame work from external `requestAnimationFrame` cadence. It also measures cold WebGL initialization, texture upload, bounded cache pressure, Atlas sprite rendering over 250 to 10,000 route-sized screens, and selection/mount/load/removal of four same-origin iframes. Renderer identity, software/native adapter evidence, three heap lifecycle phases, latency class, and every workload invariant remain explicit. `pnpm benchmark:web` adds five isolated Chromium homepage loads with cold LCP, TTFB, DOM readiness, load, CLS, DOM size, and a strict 50 ms maximum-main-thread-task gate. See [verification](./verification.md#performance-benchmark).

The production Studio has separate startup and board contracts. Every build emits `manifest.json` plus schema-version-3 `studio-build-report.json`, measuring the complete static entry graph against 300,000 raw and 95,000 gzip-byte JavaScript budgets. The gate requires Atlas, Editor, Notes, Doctor, and Settings to be dynamically reachable destinations, defers modal overlays until opened, rejects any Pixi or GPU canvas module in the initial shell, and requires both the Markdown/SARIF/HTML review renderer and strict schema/protocol validation to remain reachable on-demand chunks. The disconnected graph factory and optimistic flow-record transforms are validation-free; every untrusted daemon payload and every flow candidate still crosses the strict lazy validation boundary before entering Studio state. `pnpm verify:studio-runtime` first opens production without a daemon and requires an explicit zero-route, zero-component offline state with no Fieldbase substitution; it then proves a disconnected note write fails without mutating state, a direct Notes route requests no Pixi assets, and a direct Atlas route promotes the deferred GPU runtime. `pnpm verify:studio-boards` opens all 23 shipped states at exactly 1440 × 900, records geometry, route identity, theme, renderer telemetry, errors, timing, and screenshots, and fails on any drift from the public `studioBoards` and `studioFrame` contract. `pnpm verify:studio-profiles` proves isolated Owner and Customer origins, headers, cookies, local storage, Vite-style WebSockets, clean post-bootstrap URLs, and capability exclusion from LLM context. Runtime timings retain their observed machine and browser meaning; they are evidence, not universal limits.

## Studio extension API

Topo offers the same keyed add, edit, and remove model at two levels. An installed project can add a sandboxed loopback destination and navigation command directly in `topo.config.ts`; the daemon serves the normalized versioned manifest, Studio composes it over the built-ins, and invalid semantic composition falls back to the complete base Studio with a visible issue. A source build uses `customizeStudio({...})`: a new destination needs only `{ component }`, a command may be one runtime function, and custom views receive one organized `useStudio()` runtime with `actions.go(destinationId, view?)`. IDs derive labels and kebab-case routes in both paths. Advanced path, icon, canvas-tool, primary-action, status, and lazy-component fields remain available to source extensions without entering the installed-project contract. The route matcher, destination menu, command palette, chrome, and status bar all consume the resulting immutable definition. The installed CLI consumer fixture and source review-queue fixture both prove removal and addition without shell changes. See [Studio extensions](./STUDIO_EXTENSIONS.md).

## Adapter scaffolding

`topo adapters create` turns the five independent extension families into one approachable workflow. A developer selects `framework`, `api-endpoint`, `flow-discovery`, `component-preview`, or `application-runtime`, supplies a stable ID and label, and receives a zero-dependency ESM module, executable Node contract test, README, and version-one `adapter.json` manifest. `--dry-run --json` exposes the exact four-file plan without writing; a real `--json` create emits one post-write `created` result. A custom `--output` must remain one directory under `topo/adapters/` so its manifest stays discoverable. Existing targets are conflicts, linked output ancestors are rejected, and application is staged in a temporary sibling before one directory rename, so Topo never merges into or overwrites existing adapter code.

The generated module is a contract-valid no-match starting point rather than guessed framework behavior. Its output includes the exact `topo.config.ts` registration entry, and the packaged CLI consumer runs the generated test, loads the framework module through the real workspace registry, and queries its canonical context record.

`topo adapters check [path] [--id <id>] --json` adds one bounded conformance report across all five extension families. Each selected scaffold receives explicit `manifest`, `module`, `identity`, and `empty-context` checks. The last check executes the real framework, API-endpoint, or flow-discovery registry, component-preview registry plus capture-URL resolver, or process-free application-runtime resolver against a safe read-only context. Malformed manifests, missing IDs, import failures, identity drift, and contract violations remain visible issues. The command imports local adapter code but never starts the application or a development server; a passing report must still be followed by a real-project scan or runtime test.

`@topo/adapter-inventory` merges the built-in catalog, project manifests, configured module specifiers, and framework, API-endpoint, flow-discovery, or component-preview adapter IDs observed in the normalized graph into one schema-version-1 response. Every entry distinguishes `active`, `registered`, `declared`, and `available`, carries exact `screenIds`, `endpointIds`, `flowTransitionIds`, `inferredFlowIds`, and `componentIds` behind its counts, and preserves manifest parse failures. The daemon serves this response from `GET /adapters`, watches `topo/adapters/*/adapter.json`, emits a typed `adapters` resource invalidation, and Studio renders the same grouped inventory instead of inferring framework state. Context schema version 7 projects every inventory entry as an `adapter` record with source plus exact bidirectional route, screen, endpoint, transition, journey, and component relationships; malformed manifests remain visible as `issue` records. See [adapter authoring](./ADAPTERS.md#adapter-inventory).

## Cache management

Topo exposes one derived-cache contract everywhere: `inspectProjectCache(projectRoot)` and `cleanProjectCache(projectRoot, { dryRun })` in `@topo/cache`, `GET /cache` and `POST /cache/clean` in the daemon, `topo cache inspect|clean`, and `data.cleanCache()` from Studio's `useStudio()` runtime. Reports are versioned JSON with byte, file, directory, symlink, and top-level-entry totals. Studio shows live evidence when connected and labels demo or offline state explicitly.

Cleanup authority is exactly `<projectRoot>/.topo/cache`. Traversal never follows a symbolic link, targets are containment-checked, dry runs do not write, and a real cleanup recreates an empty cache directory. Notes, flows, snapshots, component previews, LLM exports, installation metadata, and `.topo/state.json` are retained because they are review or runtime evidence rather than working cache entries.

## Reversible project setup

`topo init` separates detection, planning, and application. It detects the package manager, monorepo shape, Next.js or TanStack applications, Storybook, Playwright, fixtures, and mocks, then prints every proposed directory and file change. Multiple application candidates require `--app <path>`; malformed or legacy install manifests and conflicting package scripts fail before writes begin. `--dry-run` and `--json` expose the same immutable plan without changing the project.

Applying a ready plan uses stale-plan checks and rollback, writes a version-3 `.topo/install.json` last, and records hashes plus prior contents for every managed file. `topo uninstall` refuses to touch drifted files. When managed files still match, it restores modified files, removes unchanged generated files, and removes only empty directories, so user-authored notes or flows survive. The initializer stages the package dependency and script but prints the package-manager install command instead of mutating a lockfile behind the developer's back.

`topo migrate` applies only registered metadata migrations through immutable, schema-versioned plans. The first registry step upgrades installation manifests from version 2 to version 3 by adding explicit package-spec and update evidence; unsupported versions remain visible conflicts and are never guessed. `topo update` reconciles the project to the running CLI version, changes only the tracked Topo package spec and lifecycle manifest, preserves unrelated `package.json` fields, refreshes the future uninstall baseline, rejects project-owned `topo` scripts, and prints the package-manager install handoff without executing it. Both commands support bounded `--dry-run --json` evidence and stale-plan rejection. Canonical LLM context exposes only sanitized lifecycle metadata in the project record; file hashes, prior contents, and rollback material remain local operational evidence.

## Local Studio runtime

`topo dev <project>` starts the complete local stack through one `@topo/local-runtime` handle. That module transactionally starts or reuses the native application, creates isolated profile gateways, starts the daemon, and serves the compiled Studio; a failed stage rolls back everything already started and one idempotent close releases every listener. The CLI only resolves options and presents public evidence. `@topo/studio-host` validates the bundle root and every real resolved asset, serves client-side deep links without colliding with daemon routes, injects the actual daemon origin into the otherwise static HTML, and shuts down with the daemon. It binds only to loopback, applies a strict content-security policy that admits snapshot, baseline, and diff images only from that exact daemon origin, streams hashed assets with immutable caching, keeps the HTML uncached, and loads Pixi's generated-function-free synchronization path only with a GPU destination so the shell remains both CSP-compatible and small.

For a loopback application, the same command creates one signed gateway origin per configured preview profile and adds only those exact origins to Studio's frame policy. Studio waits for the complete graph-and-session hydrate before promoting a live iframe, preventing a clean capability-protected origin from being requested before bootstrap. Port 4173 is preferred. If it is already occupied and the user did not request an exact `--studio-port`, Topo chooses a free loopback port and prints the authoritative Studio URL. `--preview-port` provides a temporary native-origin override, `--no-studio` retains daemon-only operation, and `--studio-dir` supplies an explicit production bundle. The CLI builds the same source Studio, runs the same manifest inspection, and ships its passing machine-readable build report in the self-contained package tarball with no private `@topo/*` runtime dependencies. The packed-consumer validator requires the version-two five-check report and emits raw/gzip startup bytes plus destination, Pixi, and review-export deferral in its own JSON result. The release contract binds the packed manifest, build evidence, public/provenance settings, runtime dependencies, and optional `v<package-version>` release tag into that result. CI installs and exercises the tarball in an isolated fixture. A guarded GitHub release workflow retains and publishes that exact verified artifact through token-free npm OIDC only after external npm ownership and trusted-publisher setup. This packaged preview does not mean `@topo/cli` has been published to npm.

Studio's data authority is fail-closed. A normal production URL begins in **connecting** state with an empty normalized graph and empty notes, flows, captures, adapters, and findings; a failed hydrate becomes an explicit **offline** state without borrowing the Fieldbase demo. If a previously connected daemon drops, Studio may continue displaying that session's last validated records but labels them as last-known evidence. Resource events may coalesce into overlapping full hydrations, so each hydrate receives a monotonic lease and only the newest request may commit validated collections or connection state. Disconnected production note and flow mutations are rejected before optimistic state changes because an in-memory edit would not be durable; only explicit demo mode permits temporary local mutations. Review previews derive the current project name, finding count, and coverage gaps from that same graph instead of hard-coded demo copy.

Studio keeps every visible `input`, `textarea`, and `select` in its DOM overlay layer associated with a real label and a stable form name. Compact Paper-matched controls use visually hidden labels rather than placeholders as their only name, while all-caps section captions use semantic text instead of orphaned label elements. Flow and note authoring, command and catalog search, and Settings selectors therefore remain screen-reader addressable without changing canvas geometry. Dark and light semantic caption and error colors retain at least `4.5:1` contrast against their actual surface tokens. The production 23-board verifier audits form semantics and those rendered token pairs on every destination and state.

Every daemon value consumed by Studio is parsed at runtime. Canonical note, flow, route-snapshot, graph, and evidence records live in `@topo/schema`; `@topo/protocol` owns versioned browser response envelopes. `GET /project` returns the exact package-derived name, project and source roots, config path, and a version-one sanitized capture policy. Studio therefore presents `topo.config.ts` auto-capture, headless, and viewport values as project-owned evidence rather than browser-local toggles. Theme, bounded one-to-eight live-frame capacity, hover promotion, selected profile, and runtime-diagnostics opt-in are the only local preferences; each changes real Studio behavior. One synchronous exclusive action lease covers rescans, captures, diagnostics, exports, cache work, and note or flow writes before React can render a busy state, so rapid repeated input cannot launch two mutations or apply two optimistic patches. Create and update responses are validated before replacing optimistic note or flow state. Invalid secondary resources retain the last valid value, while invalid graph data never marks the session connected. Malformed Markdown notes and JSON flows remain explicit issue counts in their collection envelopes.

## Native application runtime

`topo dev` now completes the local runtime chain: it first probes `preview.baseUrl`, reuses a healthy server without taking ownership, or starts the application's existing `dev` package script and waits for HTTP readiness before opening the daemon and Studio. Next.js, TanStack, Nuxt, and Vite adapters add the configured loopback host and port; Vite covers ordinary React, Vue, and SvelteKit projects, while a generic `dev`-script adapter remains the conservative fallback. An explicit tokenized `preview.server.command` or project-installed `extensions.applicationRuntimeAdapters` entry handles uncommon frameworks without adding conditionals to the CLI.

Automatic startup is limited to unavailable loopback HTTP origins. A remote or HTTPS origin is reuse-only, `external` mode requires an already-running server, and `managed` mode refuses to take over an occupied origin. Topo retains only the latest bounded process output for startup evidence, reports an unexpected exit, and stops only the process tree it owns. `--no-app` opts out entirely. Invoking `topo dev` can execute the inspected repository's existing `dev` script; source scanning and the other read-only commands do not.

## Signed preview gateway

`topo dev` automatically places each configured local preview profile behind a different loopback host. A profile's opaque, expiring launch URL performs one signed bootstrap, initializes its configured local storage, establishes partitioned session state, and replaces itself with a clean URL. Profile headers and configured cookies are applied server-side. Upstream HTTP, redirects, response cookies, and Vite-style WebSocket/HMR traffic continue through the application's native development server. For eligible UTF-8 HTML responses inside that signed boundary, the gateway injects one versioned, credential-free preview bridge and adds only its exact hash to the existing script policy. The bridge keeps a bounded sanitized navigation, network, DOM, and error event queue, supports correlated snapshot and live-event subscriptions from its exact loopback parent, and answers exact-parent requests for semantic element evidence. Non-HTML, compressed, oversized, unsupported-charset, remote, or unsigned responses are never instrumented.

The gateway adapts only framing restrictions and cookie attributes needed inside this signed local iframe environment. It preserves other content-security directives, rejects remote targets and reserved header overrides, bounds request bodies, and closes all sockets deterministically. Production authentication and production headers remain unchanged. Runtime session descriptors are available to Studio from `GET /preview/sessions`, but signed capabilities, headers, cookies, and local-storage values never enter the graph, durable state, or LLM exports.

## Monorepo project model

Topo resolves every command into two explicit roots. `projectRoot` is the directory passed to the CLI; it owns `topo.config.ts`, `.topo/state.json`, notes, flows, captures, preview artifacts, jobs, and LLM exports. `sourceRoot` is `projectRoot/config.rootDir`; it owns framework files, source-relative graph paths, static analysis, standalone component construction, and the native development command. A single-package repository uses the same directory for both.

Project-installed framework, API-endpoint, component-preview, application-runtime, and flow-discovery adapter modules resolve from `projectRoot`, so a monorepo installs extension packages once. Discovery adapters still receive the immutable source snapshot or package metadata for `sourceRoot`. Flow discovery reuses that snapshot and receives canonical screens plus bounded source reads; it never triggers a second filesystem walk. The daemon watches source changes under `sourceRoot` and authoritative note or flow changes under the project `.topo` directory without storing a second state tree inside the application package. LLM context schema version 7 names both roots explicitly, adds project-owned adapter manifests, and retains `rootDir` as a source-root alias for readable migration.

`rootDir` names the application source directory independently from Topo's durable project directory. It may be `.`, a nested or adjacent relative path, a platform-native path, a directory link, or an absolute path; project resolution trims the value and proves that the selected target exists and is a directory before a scanner or application command runs. `projectRoot` remains the sole authority for `.topo` notes, flows, state, captures, cache, installation metadata, and LLM exports, while `sourceRoot` is used only for application reads, watching, preview construction, and native commands. Doctor's stable `application.source-selection` check warns when an unscoped project root produces screens from multiple framework families, while an explicit source or one-family root passes with its exact selection evidence. The same check is available to Studio, bounded context queries, JSONL, and MCP as an ordinary `doctor-check` record.

## Compiler-grade source intelligence

Topo parses JavaScript, TypeScript, JSX, and TSX through the native `oxc-parser` binding rather than regex-shaped source guesses. The small versioned read model retains value imports and aliases, value re-export dependencies, callable exports, source lines, conservative required-prop counts, and recoverable parser diagnostics without exposing the compiler AST to scanner or adapter callers. A bounded source-identity cache reuses unchanged modules across daemon scans.

The daemon owns one serialized scanner session for its lifetime. A complete scan discovers and reads the full source tree; a watched refresh updates only the reported source entries while retaining unchanged source and the already loaded framework, API-endpoint, and preview adapter registries. New or removed directories, invalid paths, and explicit manual rescans fall back to complete discovery. Every refresh still runs the ordinary adapters and rebuilds the complete normalized graph, so extension authors receive the same narrow immutable source-snapshot contract and do not need an incremental API.

The scanner reads each discovered source file once, runs independent framework and preview adapters concurrently, and follows only snapshot-contained relative module relationships. Route coverage therefore reaches components through intermediate feature modules and value barrels while type-only imports do not become runtime usage. An Oxc error does not erase the route graph: the affected component becomes explicitly blocked and the exact file, line, column, severity, and compiler evidence become an ordinary finding readable by Studio, exports, context queries, and MCP. Topo still does not execute project source during discovery. See the [Oxc parser documentation](https://oxc.rs/docs/guide/usage/parser).

## Framework adapters

The scanner is framework-independent. Next.js, TanStack, React, Vue, Nuxt, and Svelte adapters satisfy the same versioned adapter interface, and project-installed adapters can be registered without changing scanner internals. Permanent native fixtures cover Next.js App Router, Next.js Pages Router, TanStack Router, TanStack Start, React Router, Vue Router, Nuxt, and SvelteKit through one machine-readable compatibility gate: source scanning, canonical LLM flow and step records, managed native development processes, real Chromium routes, stable screen identities, runtime errors, and deterministic shutdown. The App Router fixture proves multiple graph states for the same route, including `loading` and `not-found`, without hiding them behind browser-only paths. React and Vue read only static absolute route declarations and expose routerless application roots without executing project source. Nuxt and SvelteKit follow their public file conventions, including parameterized routes. TanStack prefers complete generated `fullPath` declarations and uses filename inference only when no generated contract is available. Every adapter normalizes its parameter syntax into the cross-framework `:param` graph form and requires project-owned concrete preview examples before browser execution. See [built-in adapters](./ADAPTERS.md#built-in-framework-adapters) and [verification](./verification.md#framework-compatibility-fixtures).

Component preview discovery is a separate extension family. `@topo/preview-adapter` gives each preview system a narrow, versioned discovery and runtime-resolution contract; `@topo/workspace` composes built-in Storybook and Topo adapters plus project-installed preview adapters without coupling them to framework route discovery. Projects register modules through `extensions.componentPreviewAdapters`. `preview.componentBaseUrls` supplies local origins only for external runtimes such as Storybook; the built-in Topo runtime is daemon-managed.

## Capture and screen states

Topo uses the application’s native development server for routes. Playwright workers capture real routes into `.topo/snapshots` and resolved component preview variants into `.topo/previews`. Static routes use their canonical path. Parameterized routes use a validated `preview.routes` example while every snapshot retains both the canonical `routePath` and actual `previewPath`; unresolved patterns fail closed before Chromium launches. A component capture waits for its adapter-declared ready selector and watches an optional error selector; blank loading documents and visible preview failures are not persisted as successful images. Durable metadata retains status, dimensions, timestamps, content hashes, adapter identity, and exact source identity. One failed component variant is recorded as evidence without aborting the remaining batch.

Watched source changes are batched and serialized. Exact route source changes recapture only their screen; component source or preview changes recapture the component and every known consuming screen. A shared or otherwise unattributed rendering dependency conservatively invalidates all visual entities. Unaffected capture status survives graph reconciliation, while invalidated screens become `unseen` until their evidence is refreshed. Automatic capture is enabled by default and can be disabled with `preview.autoCapture: false` without disabling graph watching.

The capture policy crossing browser and agent boundaries is intentionally smaller than the full preview configuration. Its version-one schema contains only `autoCapture`, `headless`, and positive integer viewport dimensions. Executable paths, cookies, headers, local storage, profile values, and signed sessions are excluded. Studio reads the policy from `GET /project`; bounded `project` context queries read the same object from `topo.config.ts` evidence.

The loopback daemon lists metadata with same-origin, extension-bearing `/image.png?v=<contentHash>` URLs so Pixi and ordinary browsers select the PNG loader deterministically and never retain a stale texture after recapture. The prior `/image` routes remain compatibility aliases. Each endpoint streams root-contained, no-store bytes; Studio never needs a raw local filesystem path. Typed `graph.updated` and `resource.updated` events cover graph, note, flow, snapshot, visual-baseline, visual-comparison, component-preview, and interaction-probe state. Studio validates every event at runtime before rehydrating durable data.

## Visual baselines and comparisons

Any successful route snapshot can be accepted as that screen's local visual baseline from the Studio inspector or `POST /visuals/baseline`. Acceptance is explicit: Topo never turns a new capture into review authority automatically. The baseline retains the immutable snapshot path, SHA-256 content identity, dimensions, route, screen, source snapshot, and acceptance time. One screen has one current baseline, so replacing it is a small, predictable operation.

Every later successful capture compares itself to the accepted baseline. Equal hashes return an unchanged result without decoding either PNG. Changed hashes are decoded once and compared with Pixelmatch; equal-size images produce exact changed-pixel counts, ratio, threshold, and a hash-addressed PNG under `.topo/comparisons`. Dimension changes remain a typed `dimension-changed` result rather than being stretched into misleading pixels. A failed comparison is evidence and does not turn a valid route capture into a failed capture.

`GET /visuals` exposes baseline and comparison metadata plus root-contained image URLs. Studio shows baseline authority, changed-pixel metrics, baseline and diff thumbnails, and a single accept-current action in the selected screen inspector. `visual-baseline` and `visual-comparison` context records preserve the same relationships and `topo://visual-*` image resources for CLI, JSONL, daemon, and MCP readers.

## Component preview coverage

Component discovery reports what can be rendered and what is missing a usable preview. The component canvas groups every discovered component by coverage state, keeps selected-component identity at the world origin, projects each `usedBy` reference as a resolved or unresolved route node, and hydrates the selected captured variant as a GPU texture. Selecting a route consumer opens that route in the same Atlas session. The sidebar and inspector remain accessible DOM controls while the topology stays GPU-rendered.

The Storybook adapter discovers only named exports from colocated story modules, records their exact source lines, and resolves them against Storybook's live `/index.json` or compatible legacy `/stories.json`; Topo never guesses a story ID. Each discovered variant records its exact component source, story export, adapter ID, resolved index ID, and capture artifact. A story index that is unavailable or stale produces an actionable failed artifact. The permanent Storybook 10 React/Vite fixture and `pnpm verify:storybook` build the actual static index, serve it on loopback, render every state in Chromium, and require content-addressed PNG evidence.

The built-in Topo adapter pairs `components/X.topo.{js,jsx,ts,tsx}` with `components/X.{js,jsx,ts,tsx}`. Every zero-required-prop function, default function, or simple arrow-function export in the colocated preview file becomes an explicit variant with an exact source line and export name. Projects can also key one object or a list of exact wrapper exports under `preview.components[componentFilePath]`; this makes required-prop components renderable without writing an adapter. Marking a configured source `provenance: "ai-accepted"` records a deliberate acceptance decision but does not authorize Topo to generate or modify source. Component and source paths are contained POSIX paths, and missing files, missing exports, or wrappers with required props fail closed with actionable evidence.

The connected component inspector can explicitly create the conventional colocated file through **Create preview draft**. `@topo/preview-scaffold` owns this mutation behind a renderer-independent inspect/apply API; Studio sends only the stable component ID to the loopback daemon and accepts the returned graph only after shared protocol validation. The source-writing endpoint rejects non-loopback browser origins while retaining origin-less local process callers. Topo never overwrites an existing target, rejects escaping or linked-outside-root sources, and records source plus template hashes. A zero-required-prop component receives an immediately discoverable `Default` preview. A required-prop component receives an intentionally inactive typed fixture draft with no renderable export, so Topo cannot claim coverage before deterministic values are supplied. The scanner keeps that draft visible as a source-located `component-preview-draft:<component-id>` finding, which reaches Studio, bounded context queries, JSONL, and MCP through the ordinary finding contract.

Source priority is deterministic: Storybook (`100`), colocated Topo previews (`200`), configured project exports (`300`), automatic zero-prop Topo exports (`400`), and accepted generated exports (`500`). Lower values win; external adapters without an explicit priority also use `500`. Every source records `storybook`, `colocated`, `configured`, `automatic`, or `generated` discovery provenance. A component is `renderable` only when an adapter emitted at least one exact preview-source record.

When capture selects a native Topo source, the daemon lazily starts one Vite/React runtime on an ephemeral loopback port and reuses it until shutdown. Its URL includes a 256-bit capability segment, accepts only allow-listed source extensions inside the project root, and reports `loading`, `ready`, or `error` on the document element. Its runtime error panel includes source, export, and error text for both humans and Playwright evidence. The component inspector shows provenance beside adapter identity. Storybook-only work does not start this runtime.

## Notes and review

Notes are separate, versioned Markdown files under `.topo/notes`. A note can target a route or an explicit entity kind and remains readable without Topo running. Its review lifecycle (`open` or `resolved`) is independent from its anchor health (`unbound`, `attached`, `drifted`, or `orphaned`). Anchor evidence can retain source identity, component symbol, accessibility role and name, test locator, DOM fingerprint, normalized coordinates, drift distance, and the last verification time. Missing signals stay explicitly **Not recorded**; Studio does not invent them.

The CLI crosses the same note-store interface for `list`, `add`, `show`, `update`, and `remove`; it never edits Markdown with command-specific parsing. Adds may use a deterministic namespaced ID. Updates patch content, lifecycle, route, author, or explicit entity target and provide deliberate clear operations instead of empty-string conventions. Every mutation validates note type, target kind, and status before writing, supports complete JSON output, persists atomically, and refreshes canonical LLM context before reporting success. The packed-consumer contract exercises that complete lifecycle and requires the projected note record to appear after creation and disappear after deletion.

The annotation palette opens a complete typed composer instead of immediately writing a placeholder note. Its eight visual choices map visibly onto the seven canonical note types: **Flow marker** is a free-standing `flow` note, not a hidden eighth schema value. Element, screen, and region choices record only the explicitly selected screen identity and route; element and region coordinates remain unbound until real placement evidence exists. A flow note records an explicitly selected flow step when available, otherwise the selected flow. Checklist, decision, canvas note, and flow marker remain free-standing even when a screen happens to be selected. Before saving, the composer shows the exact durable target—or **No durable target**—and submits one ordinary `WriteNoteInput` in both daemon and offline demo modes.

Studio filters notes by lifecycle, drift state, and type, then searches the visible facet across Markdown title and body plus route, author, lifecycle, type, and structured anchor evidence without changing record order or source authority. The detail view is inspect-first: source, note content, anchor health, and previous/next record navigation remain visible by default, while title/body editing and deletion are disclosed only on request and cancellation restores the accepted record. It uses the shared rounded Pixi evidence canvas to promote the note's exact signed live screen, newest capture, or an explicit unbound state. Its route navigator uses the same entry-first, hierarchy-aware, static-before-dynamic ordering as Atlas and Doctor and automatically reveals a changed selection. A note resolves to a screen only through its exact screen target, canonical route, recorded source identity, or an explicitly targeted component's `usedBy` relationship. Recorded normalized coordinates render as a note-colored point or region over that evidence; absent coordinates never produce a fabricated marker.

Element and region notes expose an explicit placement mode on that exact evidence artboard. A click records a normalized point for an element pin; a drag in any direction records a canonical normalized rectangle for a region note, while accidental tiny drags remain uncommitted. Placement suspends iframe and camera input only for the duration of the action, previews the pending geometry, and persists the screen target, source, coordinates, attached status, and verification time through the existing note update contract. On a signed live screen, an element pin also asks the preview bridge for the current hit element's role, accessible name, stable test locator, and bounded DOM fingerprint. That current inspection replaces prior semantic signals; a missing or unavailable bridge produces truthful coordinate-only evidence and clears old element signals rather than preserving them across a move. The separate Re-anchor action may preserve recorded signals only when its exact screen identity does not change. Moving or re-anchoring to a different screen drops the previous screen's coordinates and DOM signals instead of relabeling stale evidence. The inspector also edits title and body, resolves or reopens the note, and removes it through an explicit two-step action. Mutations are optimistic, acquire the shared action lease before changing local state, and roll back on a daemon error. `GET`, `POST`, `PATCH`, and `DELETE` note endpoints validate the same strict contract and refresh deterministic LLM context before emitting `resource.updated`. Direct edits to note Markdown or flow JSON receive the same resource refresh without forcing an unrelated graph scan.

## User flows

The renderer-neutral flow scene remains readable as the catalog grows: variable-width lanes pack into bounded centered landscape rows, while normal focus keeps the selected flow readable and retains its nearest supporting lane as contextual evidence below or beside it. The selected step remains anchored at world origin, and packing never creates, removes, or redirects an explicit edge.

Flows are versioned JSON records under `.topo/flows`. Each step can carry a route, screen, action, expected result, note references, and one or more next steps. Studio creates flows, edits metadata and lifecycle, adds or removes steps, binds routes, selects an entry step, and connects explicit branches from the same inspector that renders the resulting topology. That inspector opens in a compact evidence mode: source, coverage, the first break, selected-step facts, and an ordered resolution-aware step navigator remain visible without surrounding them with form controls. Metadata and step editors disclose independently, preserve explicit cancel behavior, and keep every prior mutation available. The flow catalog scrolls independently and returns changed selections to view. Updates acquire the shared action lease before applying an optimistic patch and restore the previous record when the daemon rejects them; deletion requires an explicit second action. The CLI can list, show, add, apply complete JSON, patch metadata, and remove flows with structured output.

**Trace flow** starts an ephemeral recording session at the selected flow's explicit entry route, or the selected screen when no flow is selected. The route canvas subscribes to the exact signed live iframe, records only new navigation events, deduplicates reload snapshots, maps concrete dynamic URLs back to canonical graph routes, and shows the current path and step count without hiding the application. **Cancel** discards the session without writing. **Finish** projects the observed sequence into ordinary linear `nextStepIds` and creates one existing version-one flow through the same validated Studio and daemon mutation path. Network, DOM, and error observations never become flow steps, and the transient bridge queue never becomes a second flow authority. After persistence, the saved JSON and ordinary `flow` and `flow-step` context records are immediately available to Studio, CLI, bounded queries, and MCP.

The flow store validates stable flow and step identities, preserves creation time, supports an explicit entry-step clear, percent-encodes namespaced IDs instead of collapsing them onto hyphenated filenames, and serializes read-modify-write operations across independent store instances. Malformed files remain visible as issues. Every accepted daemon mutation persists JSON, refreshes canonical `flow` and `flow-step` records, and emits a typed flow invalidation before Studio rehydrates.

The flow canvas lays out explicit `nextStepIds`, stacks branches at a shared graph rank, marks route bindings as resolved, unresolved, or unbound, and reuses existing route snapshots by `resolvedScreenId`. Fit frames the selected lane with deliberate trailing stage space so its nearest focused lane can remain visible as context without shrinking the primary journey; Fit Atlas reveals every recorded flow. Flow records, bindings, artifact references, and the exact renderer-neutral scene are independently queryable by agents.

Source-derived journey candidates appear in a separate **Inferred journeys** rail. They retain exact transition, source, confidence, adapter, and truncation evidence; selecting one never enables the recorded-flow editor or writes `.topo/flows`. Developers can use that evidence as a review map, then deliberately record or trace the journey when it should become authoritative.

## Review exports

One deterministic exporter produces Markdown, SARIF 2.1.0, or a self-contained HTML report from the normalized graph, findings, Markdown notes, and optional snapshot references. The Studio dialog, daemon `/review` endpoint, top-level `topo export`, legacy `topo notes export`, and MCP Markdown resource all cross this same seam instead of maintaining format-specific interpretations.

Studio loads that deterministic renderer only after an Export action begins. The production manifest contract requires the renderer to be independently loadable, reachable from the entry, and absent from the static startup graph; making it eager or orphaning its chunk fails the build. This keeps every format available without charging initial Atlas, Notes, Doctor, or Settings startup for report generation code.

Markdown retains screen coverage, source locations, evidence, note lifecycle and anchors, and an optional snapshot-reference table. SARIF emits stable rules and results plus structured Topo note and snapshot properties for automation. HTML escapes all project-authored text and embeds only its responsive report shell. Snapshot PNGs are never copied into any report; artifact paths, dimensions, timestamps, and hashes remain explicit and LLM-readable.

## Doctor report

Topo Doctor produces one versioned report instead of letting the CLI and Studio infer environment health independently. Its bounded checks cover the Node.js runtime, exact Playwright Chromium executable, loopback daemon binding, preview-origin safety, native preview reachability, explicit application-source selection, framework discovery, source coverage, unresolved parameterized-route examples, and configured preview-profile names. Every check has a stable ID, application/environment/security scope, pass/warning/error status, evidence, and optional remediation. Profile credentials, cookies, headers, local storage, signed sessions, and environment values are never included.

`topo doctor --json`, daemon `GET` and `POST /doctor`, and the Studio Doctor destination consume the same report. Studio shows the report's actual generation time and never treats a connected daemon as proof that Chromium or the preview server is healthy. Each check is also projected as a searchable `doctor-check` context record, so CLI queries and MCP clients can inspect exactly the evidence visible in Studio.

Studio preserves the report's environment, security, and application scopes as separate triage groups instead of relabeling every check as machine state. Its app count combines application readiness checks with source findings, its environment count combines environment and security checks, and severity filters compose across the complete set. No source finding is truncated from the scrollable report. A disclosed remediation action copies its exact canonical text and reports success or failure in place; Topo never executes arbitrary remediation from the browser.

The Doctor findings board is a source-backed evidence workspace rather than a static preview. Its navigator displays canonical route paths in the shared entry-first, hierarchy-aware, static-before-dynamic order instead of repeating framework filenames. Selecting a report row, search result, or evidence-rail finding writes the exact bounded finding identity into the Studio URL before resolving its screen through an exact source identity or an explicit component `usedBy` relationship. Direct links and reloads therefore retain the selected finding and open the same shared Pixi grid, camera, configured preview route, signed live iframe, newest snapshot, or labeled unseen state used by Editor. Findings and screens expose stable IDs in the DOM, and a finding without captured anchor coordinates is never displayed as a fabricated visual pin.

## Interaction diagnostics

Static analysis and isolated runtime probes gather evidence about suspicious controls. The selected-route Probe view dispatches a local Playwright run and renders the durable result instead of a canvas-only verdict. Its Paper-sized target well is a native selector over every canonical control observation on that route; choosing a control writes `probe=<stable-id>` to the Studio URL, and direct links and reloads retain that exact observation. Every control observation has a stable identity, role/name locator, route and screen relationship, timestamp, status, evidence, and typed effects for navigation, network, DOM or accessibility changes, dialogs, forms, downloads, focus, storage, application events, and runtime errors. Successful, inert, skipped, and activation-error outcomes are all retained under `.topo/state.json`, served by `GET /interaction-probes`, and projected as `interaction-probe` LLM records.

Topo never automatically declares an interaction broken. An activation with no recognized effect becomes a **possibly inert** finding with a confidence score. Static analysis recognizes both assigned and JSX boolean `disabled` attributes, so an explicitly disabled button does not become an inert-control candidate. Disabled, hidden, explicitly excluded, lexically destructive, and implicit non-GET form controls are recorded as skipped and never activated; a non-GET preview form requires an explicit `data-topo-probe="safe"` marker before the isolated worker may submit it. Ordinary click focus on the activated control is ignored so it cannot hide a genuinely inert button.

`topo check` turns that same evidence pipeline into a local/CI quality gate. Its schema-version-1 JSON report contains explicit `static` or `runtime` mode, requested routes, `info|low|medium|high|none` threshold, summary counts, findings, probe artifacts, and the process decision without repeating the full graph. Static checks default to failing on open `low` findings. Runtime checks are opt-in, may be narrowed to one canonical route and preview profile, and treat a requested activation error as blocking whenever failure policy is enabled.

Studio keeps that opt-in meaningful: when **Playwright diagnostics** is enabled in browser-local Settings, re-running Doctor performs the ordinary environment report and then the bounded runtime diagnostic pass for the selected preview profile. With the preference disabled, Doctor does not launch interaction probes.

## LLM and MCP access

Topo bounds operational history as well as query output. Long-running queued or running jobs remain observable and the newest 100 durable completed or failed jobs are retained by default. Sub-frame source scans are transient queue telemetry: they remain visible while active but do not fill `.topo/state.json` or canonical job history after completion. Startup deterministically compacts older version-one files, and `jobHistory` records the configured limit, retained count, and cumulative pruned count. `GET /jobs` exposes the same versioned retention evidence, and the canonical `project` context record includes it so an agent can distinguish durable history, an active queue, and intentionally pruned terminal operations.

Every durable product concept enters one canonical read model. Schema version 7 includes complete `api-endpoint`, `flow-transition`, `inferred-flow`, and `inferred-flow-step` records alongside project recognition, malformed source issues, sanitized `preview.routes` configuration, version-one capture policy, route preview resolution, component atlas placement, and actual capture/probe paths. Route hierarchy placement translates renderer-family IDs into canonical schema-v7 route IDs and adds reciprocal `parent-route` and `child-route` relationships, so JSONL, bounded queries, daemon clients, and MCP can traverse ancestry without interpreting canvas-only identities. The model also includes local `adapter.json` manifests, exact adapter-owned screen, endpoint, component, transition, and inferred-journey memberships, and reciprocal ownership relationships, while malformed adapter, API-contract, note, and flow records remain visible issues. Agents can use deterministic Markdown and JSONL files, bounded CLI queries, local daemon endpoints, or the read-only MCP server. Source-watcher scans and their resulting captures refresh this projection in the same serialized lifecycle, so graph relationships, inferred journeys, and visual-evidence status do not drift into separate agent views. See the [LLM interface](./LLM_INTERFACE.md).

Context projection builds one screen index per graph for canonical route identities, exact screen lookup, and source-to-screen relationships. Notes, flows, findings, probes, and adapter evidence therefore reuse the same closed-world lookup rather than repeatedly scanning the graph. Every output retains the same complete record envelope and relationship-integrity pass; malformed or dangling evidence remains visible instead of becoming a performance shortcut.
